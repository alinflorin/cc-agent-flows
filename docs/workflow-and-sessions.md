# Workflows, sessions and the engine

The org-chart workflow, trigger nodes, follow-up messages, the engine, analytics and cron. Part of the project notes; the overview is in `CLAUDE.md`.

- **Workflow and sessions** (`src-tauri/src/workflow/`, UI `workflow/Workflow.tsx` + `workflow/WorkflowEditor.tsx`, `Sessions.tsx`, `session/SessionView.tsx`): the app has any number of workflows (`<app data>/workflows/<id>.json`: name, instructions that every agent gets before its profile's system prompt (`combine_system_prompts`) and the org chart; a session picks one before it starts) and any number of sessions (`<app data>/sessions/<sid>.json`: name (empty = untitled, editable), task (the user's first chat message), created, status, `autonomy` `ask|never`). The workflow is an **org chart**, not a sequence: nodes are agents (`profile`, `prompt` = its role in this workflow, `max_calls` = how many times it may be called in a session (1 to 500, bounds loops), `timeout_mins` 1 to 480, default 30) and an edge `A -> B` means A may hand work to B. Other node kinds are the user: `ask` (an agent with an arrow to it may put its questions to the user directly) and `approve` (a gate on the way, `A -> gate -> B`: each handover needs the user's approval). A second edge kind, `before` (dashed, between two agents), is an order: B may be called only after A has finished, within the same coordinator's call; the engine refuses a decision that breaks it and says why, the agent may call them again later (loops); order loops are rejected on save. The **root** is the one node nobody hands work to (it gets the user's request); an agent with outgoing edges is a **coordinator** (it decides what to delegate, in what order, how often: "for each" and review loops are the agents' doing, written in their prompts, there is no loop node), one without is a worker. Edited visually with `@xyflow/react` (select an arrow to set approval). `Workflow::call_edges` (agent to agent, through gates), `ask_node`, `must_precede` and `root` are the views the engine uses. `Workflow::validate` rejects unusable data on save; `problems` (empty, no/many roots, unreachable, unknown profile, unused human node, gate without target, trigger without target, cron without request, chat node without target) are soft, returned as codes the UI translates. The app ships no workflow: a new one starts empty (the tests use the fixture `model::tests::standard_workflow`, an org chart of an orchestrator, a project manager and specialists with order arrows between them). How a team works together (who is called, in which order, how often, who moves tickets) is in the nodes' prompts and the arrows; the engine only enforces the order arrows once per call. Not built: the engine's own choice of how many instances, a separate planner LLM (the coordinators play that role), run views beyond the session page, access of the agents to Jira/GitHub (no credentials reach the VM; today only profile env vars, in plain text; ticket text is untrusted input, so use least-privilege tokens).
- **Trigger nodes and follow-up messages** (`workflow/ (`model.rs`, `store.rs`, `commands.rs`)` `NodeKind::{Chat,Cron,Webhook}` + `Node.trigger` = `TriggerCfg {cron, token, autonomy}`; `workflow/triggers.rs`, `workflow/cron.rs`, `workflow/webhook.rs`; editor `workflow/WorkflowEditor.tsx`): a trigger node has no incoming arrow and one `delegate` arrow to the agent that gets the request (`Workflow::trigger_target`; `validate` refuses the other shapes). They are not agents, so they never make an agent "called" (`root()` is unchanged). **Chat** = the user's message in the app starts the session; `chat_entry()` is where the chat node points, else the root, so workflows without triggers behave as before. **Cron** = 5-field expression in local time (`workflow/cron.rs`: lists, ranges, steps, `@daily` etc., day-of-month OR weekday when both are set, no seconds), checked every 10 s by `triggers::start` over all workflows; the node's `prompt` is the request; a minute missed while the app was closed is not made up; it does not fire while the session it started last is still `running|waiting`. **Webhook** = any HTTP method to `http://127.0.0.1:<port>/hook/<token>` (Settings > Network sets the port, default 7878, `webhook.json`; loopback only, so reaching it from outside takes a port forward or tunnel, and the URL is the secret). The body, as it arrived, is the session's request, after the node's own `prompt` text if it has one; max 48 KB (413), 60 calls a minute for all hooks (429), any method is accepted; the body is the request, and for GET, DELETE and HEAD the request line `METHOD http://host/hook?query` (token left out) goes first, unknown token 404, a session that cannot start 400/429. Tokens are 128 random bits made by `save_workflow` when empty. A triggered session is `create_triggered_session` (`source` `cron|webhook`, `entry` = the target agent, autonomy from the node, default `never`) and `Host::entry()` makes `drive` start there instead of the root. The editor's side panel shows the URL, a sample sender, "run now" and the last start/error (`triggers_status`, `trigger_fire`, `cron_preview`). Tested: cron parsing, workflow rules, request composition, and the listener against the real binary with a throwaway `XDG_DATA_HOME` (not in `cargo test`: it needs an `AppHandle`). The webhook token is never put in what the agent sees (the URL line for GET/DELETE/HEAD leaves it out; keep it that way: agent text reaches logs and audit exports). The Sessions list refreshes live (`sessions-changed` event on a triggered start, plus `session-log` status entries).
  **Decided against (by the owner, do not build or re-propose unasked):** refusing manual sessions on a workflow that has trigger nodes but no chat node (they go to the root); HMAC signature checks, payload filters and auth-header options for webhooks; cron catch-up of missed minutes; a per-session budget limit; a timeout for questions waiting on the user; steering a running turn; turning an egress denial into a question; WebSockets and request-rate limits in the proxy (connection limits, data budgets and leak detection were later asked for by the owner, see Network limits and leak detection); per-profile account pinning and per-account usage in Analytics. The broken `v0.6.0` tag is left as is (0.6.1 superseded it).
  **Follow-up messages** (`session_message(id, text)`, `Session.messages`, `State.turns`): after the first message, what the user writes is another **turn** of the same session: the root runs again with a goal made of the first request, what came of each earlier turn and the new message (`follow_up_goal`); each turn has its own journal path (`r`, then `t1`, `t2`...) and its own call counts, `max_calls` apply per turn. On a finished (`done`) session the message starts a new launch (`launch` accepts `done` when there are unanswered messages); on a running one it is queued and `drive` picks it up when the turn ends (`Host::follow_up(i)`); a message that arrives as the session ends is caught under the `Sessions` lock in the finishing task. On `failed|cancelled|interrupted` it is added and continuing runs everything left plus the new turn. Resume replays the earlier turns from the journal. Limits: 5 sessions at once (`MAX_SESSIONS`), 8 VMs in the app (`MAX_TOTAL_VMS`, a run waits for a slot and can be cancelled while waiting), 200 messages per session.

- **Workflow engine** (`src-tauri/src/workflow/engine/`, UI `session/SessionView.tsx`, route `/sessions/:sid`): `drive(host, workflow, task, state, cancel, replies)` runs one session over the org chart; the logic only talks to a `Host` trait (run an agent, log, checkpoint, autonomy), so the tests use a scripted host and `RealHost` boots VMs through `runs::run_vm`. A **call** runs an agent to its end (recursive, `call()`); a worker runs once (`RESULT_SCHEMA`: status, summary, questions, `assumptions`); a coordinator runs in **turns** and answers with a decision (`COORDINATOR_SCHEMA`): `delegate` (up to 5 `{to, instructions}`, run in parallel, each to an agent it has an edge to; the engine refuses anything else and asks again once), `finish` (`result`, `success`: goes to whoever called it; from the root it ends the session) or `ask` (questions it cannot answer: they go back to its caller as `needs_input`, which then answers, asks again or assumes; from the root they go to the user). Every decision carries `notes`, the coordinator's own progress, handed back on its next turn (only within the call: a later call of the same agent starts empty; nothing persists between sessions). **No Claude session is ever resumed**: every run is a fresh VM and each prompt is rebuilt (`worker_prompt`, `coordinator_prompt`): session goal, role, what the caller asked, notes, a compact log of what it handed out, the results since its last turn, its options. The user takes part in two ways only: questions (from the root or from an agent linked to a `You` node; the others pass theirs up to their caller; refused when the session's autonomy is `never` or after 10 questions: the agent is told to assume and to list `assumptions`, shown on the agent's run) and approval gates (always asked, even on `never`; a rejection comes back to the caller as `rejected`). Limits: `max_calls` per agent, depth 8, 60 turns per call, 300 agent runs per session, 4 VMs at once (semaphore). **Resuming** replays: each agent run is journaled in `sessions/<sid>.state.json` under the path of the call (`r`, `r:<round>:<attempt>`, `r/<round>.<i>`...) with an order number; `session_continue` (interrupted, failed or cancelled) first drops the first failed run and everything finished after it (`State::rewind_failures`), then walks the same decisions taking journaled results instead of VMs, so only what never finished runs again (a root that closed the session as failed on its own decision ends the same way). The log is `sessions/<sid>.log.jsonl` (also the `session-log` event): `call_start|call_end` (a call and its parent), `run_start|run_end` (one VM), `agent` (its messages), `decision`, `decision_rejected`, `wait`, `reply`, `error`, `status`; `src/sessionLog.ts` digests it and `session/SessionView.tsx` shows a live read-only graph of the workflow (node states, active arrows, calls and tokens per agent), a side panel with the conversation (task, questions, approvals, result), a timeline, the calls of the clicked agent and a Traffic tab with that agent's live network log (the proxy's `egress` events, which `sessionLog.ts` keeps per run as `traffic`: allowed, blocked, with credentials; not seen in a real run); at startup running/waiting sessions become `interrupted`. Commands: `session_start(task)|continue|cancel|reply|get|log`, `sessions_create|rename|autonomy|delete`. Preflight (`prepare`): the workflow validates with no problems, every agent's image is built, a token is set. Status: `new | running | waiting | done | failed | cancelled | interrupted`. Tested with the scripted host only (loops over items, parallel calls, refused decisions, questions bubbling up and to the user, `never`, approval gates, limits, resume, cancel); not run against real VMs end to end, no UI test. Not built: a budget limit, a timeout for questions waiting on the user, steering a running turn (a message sent while the session works is queued for the next turn).

- `workflow/analytics.rs` (`analytics_get(project: Option<String>)`, null = all projects merged, page `Analytics.tsx`, routes `/p/:pid/analytics` and the main menu's `/analytics`, above About): tokens, duration and run counts per session, per agent profile and per day, folded from the `run_start|run_end` entries of every session log; computed when asked, in a blocking task.

- `workflow/cron.rs`, `workflow/triggers.rs`, `workflow/webhook.rs`: the workflow's trigger nodes (see Workflow and sessions). Last start and error of each cron/webhook node are in `<app data>/triggers.json`.

**What a caller sees of a result** (`engine/prompts.rs`): only the callee's `status`, `summary` (a coordinator's `result`), `data` and `questions`, never its other messages, so a JSON block it wrote in its text is lost. `data` (a string in `RESULT_SCHEMA` and `COORDINATOR_SCHEMA`, read by `decisions::data_of`, which also turns a stray object into JSON text) is the place for content that must arrive exactly as written (JSON, lists, tables, code): the prompts tell agents to put it there whole and keep `summary` for the explanation. The caller's prompt shows it after the summary in a code fence longer than any backtick run inside it, labelled verbatim and untrusted. `summary` and `data` each get a share of 60,000 characters (at least 6,000, at most 30,000 each, `Reported` results split it) and a cut is announced with the number of characters left out. `data` is also in the `decision` log entry (cut at 4,000); the session view does not show it yet. `assumptions` are not passed on.
