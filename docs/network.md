# Network and egress

The sealed agent network: the yamux tunnel, the egress proxy, allowlists, credential injection, TLS inspection, limits and leak detection. Part of the project notes; the overview is in `CLAUDE.md`.

**Network limits and leak detection** (`net/egress.rs` `Limits|Meter|Counted`, `net/leaks.rs`, `net/inspect.rs`; asked for by the owner): every run's proxy counts the bytes of the guest's connections in both directions (the guest side, so TLS framing is included) and the open and total connections. Limits: connections at once per agent (global default 64 in `network.json` `max_connections`, Settings > Network; the profile's `max_connections` overrides), data budgets per run (`max_upload_mb`, `max_download_mb`, profile only, unset by default; when one is used up the connections fail and new ones are refused, logged once, and the run is stopped as failed at the next 2 s report, since Claude's own traffic counts and the agent could not reach its API any more). The run reports `{"type":"net","up","down","open","connections"}` events (seq 0) every 2 s when they changed; `RealHost` writes the last ones as a `run_net` log entry, which the analytics fold (per session, agent, day; Analytics page and the session view's per-agent Network panel and node lines use them, speeds are derived from consecutive reports). **Leak detection** (`network.json` `leak_detection`, default on): the secrets a profile's environment takes as `${secret:NAME}` (profile or integration env, values of 8+ characters) may only go to the hosts the *profile and its integrations list* (`Spec.allow_hosts`), not the global or project lists. A request to any other host that carries the value (address, headers, a `Basic` header decoded, percent-encoded, body up to 4 MiB; a larger body to such a host is refused) gets a 403 and a log line (never the value). To read the requests, the run's TLS inspection covers every host that must not receive a protected value (`Inspector::wants`), so those runs terminate TLS for all their hosts (HTTP/1.1 only, no upgrades; tools that pin certificates would fail). It does not catch a transformed value or one sent to a host the profile lists; injected credentials are never in the VM so they are not watched. Tested with fakes (counting, budget, connection limit, refusal in headers/Basic/URL/body); not run against a real VM or real tools.

**Plain HTTP per host** (asked for by the owner): an allowed-hosts entry written `http://host` (the UI shows a ticked "HTTP" box per row, `components/HostList.tsx`, used by Network, profiles and integrations) allows plain HTTP to that host as well as HTTPS; `clean_host` keeps the prefix (`HTTP_PREFIX`), `Rules::new` splits it (`allows_http`). Every other host stays HTTPS only (CONNECT, 443). The proxy takes `METHOD http://host/path` (port 80 only, no credentials in the URL, IP literals refused) in `Proxy::serve_plain`: one request per connection (`Connection: close`), origin form, `Host` rebuilt from the URL, hop-by-hop headers dropped, same guard, limits and meter as a tunnel; `CONNECT host:80` is still refused. No TLS inspection, so no credential injection over HTTP. Leak detection: for a host the profile does not name, the whole request (path, headers incl. Basic, body up to 4 MiB with a Content-Length; chunked refused) is read and refused if it carries a protected secret, and nothing after the request is forwarded. Tested with local servers in `net/egress.rs`; not run in a real VM.

2. (Done for agent VMs.) Networking. Agent VMs have **no network card** (`-nic none`): the only way out is one virtio-serial port, `net`, whose far end is a yamux session to the app's egress proxy, deny by default (see below). Builder VMs (which run package managers and the user's image scripts) still have plain `-nic user`, open internet, as does the VM of anyone running QEMU by hand. Consequences for agents: the VM reaches only the hosts of the allowlists (HTTPS, port 443), not the LAN, not the host, not other ports, and has no IP address but loopback; the Claude token itself is never in the VM (see below). The channel test (`vm/agentd_e2e.rs`) needs no network at all.

   Egress control (built; credential injection and TLS inspection are not):
   - Allowlists: global in Settings > Network (`config/network.rs`, `<app data>/network.json`, defaults `api.anthropic.com` and `statsig.anthropic.com`) and per profile (`Profile::allow_hosts`; integrations add their hosts too). Entries are `host` or `*.host` (subdomains only, not the bare host), HTTPS port 443 only, normalized by `profiles::clean_host`. A run's rules are the union of the two (`egress::Rules`). An empty global list cuts agents off from the Claude API.
   - **Transport: a yamux session over a virtio-serial port** (`net/tunnel.rs`, the `relay/` crate; replaced the SSH tunnel through `guestfwd=tcp:` and `russh`, decided by the owner: cross-platform, no SSH). QEMU gets `-nic none` (`runs::AGENT_NIC`) and a second port `-chardev socket|pipe,id=net -device virtserialport,chardev=net,name=net` (`Serial::named(work, "net")`, a named pipe on Windows like the agent channel); the guest sees `/dev/virtio-ports/net`. `ccaf-relay` (`relay/src/main.rs` + `port.rs`, static musl binary, ~600 KB, installed in the image at `/usr/local/bin` by `setup.sh`) listens on `127.0.0.1:3128` and opens one yamux stream per connection over the port (nonblocking `AsyncFd`; reads that return end of file are retried after 50 ms, because that is what a port says until the app's end connects). The app connects to the socket after the agent channel (`runs::run_vm`), `Tunnel::start(io, proxy, log)` runs `ccaf_relay::serve` (yamux server) and gives every stream to `Proxy::serve` (`egress.rs`); the app never opens a stream towards the guest, and the guest has nothing else to reach (no NIC, so QEMU's Landlock `connect_ports` is `Some(vec![])`: QEMU may connect to no TCP port at all). `agentd` still exports `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` (and lowercase) for `claude` only, after the profile's variables (Claude Code does not support SOCKS). No authentication: the port belongs to this VM alone, like the agent channel. `ccaf-init` starts the relay in the background and it reports `0 <guest uptime>` through the fifo `/run/ccaf/tunnel` once the local port listens (`1 0` and a message in `/run/ccaf/tunnel.err` if it cannot start); `agentd` reads that before `claude` starts. If the session dies the guest's connections fail and the run fails or times out. The binaries for both arches are built by a disposable GitHub workflow (`.github/workflows/relay.yml`, `ubuntu-22.04` and `ubuntu-22.04-arm`, then deleted) and committed as `vendor/relay/ccaf-relay-<x86_64|aarch64>`; `scripts/images/fetch.mjs` copies the one for the target to `src-tauri/resources/agentd/ccaf-relay` (git-ignored), it is one of `SETUP_FILES` (part of the base stamp, so a new relay rebuilds the base). To change the relay: edit `relay/`, run the workflow, replace the two files. Local build: `cargo build --release --target x86_64-unknown-linux-musl` in `relay/`.
   - Why not the simpler options: `guestfwd=tcp:` shares one host connection among all the guest's connections (only the first works), `-cmd:` is unknown on macOS and Windows, vsock needs `vhost-vsock` (Linux hosts only), and a pool of ports has no end-of-connection signal. yamux gives flow control and many streams on one port, and works everywhere virtio-serial does.
   - Verified on x86_64 Linux with KVM: `cargo test boots_an_agent_vm -- --ignored` (with a base image built with `ccaf-relay`): `claude` (fake token) reaches `api.anthropic.com` through the relay and the port (401, the proxy logs `allowed`), the final arrives and the VM powers off (~4.8 s from QEMU spawn to exit). Unit tests: `relay/` (many streams on one pipe, a 5 MiB transfer with flow control), `net/tunnel.rs` (4 parallel CONNECTs through yamux, a denied host gets 403, the readiness check), `net/egress.rs`, `vm/agentd_e2e.rs` (the script with a stand-in fifo). Not verified: a denied host from inside a real guest, git/npm/pip/`gh` through the proxy, macOS, Windows (named pipe for `net`, never run), aarch64 (the relay for it comes from the workflow), a run with a real token, throughput of a big upload over virtio-serial.
   - Egress proxy (`net/egress.rs`): HTTP `CONNECT` on any async stream (the yamux streams), tunnel mode only, deny by default: the host must be on the run's rules, the port must be 443, IP literals are refused, and the proxy resolves the name itself and connects to an address that passes the guard (private, loopback, link-local, CGNAT, multicast, reserved and the IPv6 equivalents are refused, so an allowed name cannot reach the host or LAN). 403 with the reason on denial, one log line per connection (shown as `egress` events), at most 64 connections per run. `agentd` sets the proxy variables; with no NIC, tools that ignore them fail instead of leaking. Planned on top (inspect mode, on `hudsucker` + `rcgen`): per-profile rules `{host, mode: tunnel | inspect, inject}`, with injection naming exact hosts, never wildcards; the CONNECT host, the TLS SNI and the `Host` header must agree. The denial could become an event for the orchestrator, which may ask the user and add a session-scoped rule.
   - **The Claude token is injected too** (`injections::claude`, built in: not stored, not listed in Settings > Injections, not editable). `run_vm` adds it to each attempt's injections, last so no user injection overrides it: every request to `api.anthropic.com` (any path, any method) gets `Authorization: Bearer <token>`. The `Bootstrap` and `CLAUDE_CODE_OAUTH_TOKEN` carry only `CLAUDE_PLACEHOLDER`, so the real token never enters the VM and every run goes through TLS inspection (a CA per run is always in the bootstrap). `statsig.anthropic.com` stays tunnelled. `api.anthropic.com` must still be in the allowlist. **Not run with a real token:** it assumes `claude` accepts the placeholder, sends it as `Authorization: Bearer`, and trusts the run CA through `NODE_EXTRA_CA_CERTS`/the system bundle; the base image must be rebuilt for the current `agentd.sh` (CA install). If `claude` checks the token's format or uses another header, adjust `claude()` / the placeholder. This replaces the "token in the VM" caveats elsewhere in this file.
- Credential injection (built, `config/injections.rs` + `net/inspect.rs`; tokens stay out of the VM): Settings > Injections (`settings/Injections.tsx`, `<app data>/injections.json`). An injection has a name, rules (`host` or `*.host`, path glob where `*` matches anything including `/`, methods; empty = all), a header (default `Authorization`; framing headers refused), a format (`bearer`, `basic` with a user name, `raw`), a value source (`source`: a secret from Settings > Secrets, the default; a variable, name in `value`; or a fixed text in `value`, plain text, not for credentials) and an optional placeholder (default `ccaf-injected`). A profile env value `${injection:NAME}` expands to the placeholder (all the VM sees, for tools that refuse to run without a token) and switches the injection on for that run (`injections::prepare`, called by `RealHost::run_agent`; a missing injection or secret fails the run). The injection's hosts are **not** added to the run's allowlist: they must be listed in the profile's `allow_hosts` (or Settings > Network), else the run does not start (`runs::run_vm`, `Rules::covers`). An `allow_hosts` entry may be `${var:NAME}` (resolved at run start by `resolve_hosts`, checked as a host then; saving accepts it unchecked). The proxy hands those hosts (not the others, which stay tunnelled, `api.anthropic.com` included) to `Inspector` after the `200`: TLS is terminated with a leaf certificate made for the host and signed by a **CA generated per run** (its key never leaves the app; the certificate goes in `Bootstrap.ca`, `agentd` appends it to `/etc/ssl/certs/ca-certificates.crt` and a file for `NODE_EXTRA_CA_CERTS`/`REQUESTS_CA_BUNDLE`), the requests are read with hyper (HTTP/1.1 only, upgrades refused), the TLS SNI and the `Host` header must be the `CONNECT` host (else 421), matching requests get the header set (replacing the client's), and they go on over a new TLS connection checked against the Mozilla roots (`webpki-roots`). A path with dot segments, encoded `.`/`/` or a backslash never matches, so a rule cannot be stretched by traversal. The log says `egress: GET host/path gets NAME`, never the value. Tested with a real TLS client and server in `net/inspect.rs` (replacement, method/path/host mismatches, traversal, SNI) and the `agentd` side with fakes; **not** run against a real VM, `gh`, `git` or a real Atlassian site, and the base image must be rebuilt for the new `agentd.sh`. **Warm connections** (`Proxy::warm`, `Inspector::stock|take`, started in `runs::run_vm`): while the VM boots, the proxy connects (same allowlist check, name resolution and address guard as any connection) to the exact hosts of the run's injections (the Claude API; `*.host` rules are not pre-connected), finishes the TLS and HTTP handshakes and keeps two such connections ready; the guest's first `CONNECT` to that host takes one (200 at once, no TCP or TLS handshake with the real server) and the proxy makes another. Why two: with the flags `agentd` sets, Claude Code 2.1.316 connects to `api.anthropic.com` and to no other host (checked through a logging proxy), two connections at a time about 1 s after launch, and with a dead network it retries 10 times with growing delays (0.5 s ... 18 s). Nothing is sent on them before a guest request; one older than 25 s or closed is dropped; a task ends with the proxy. The client TLS config of `Inspector::new` is shared by all runs, so session tickets are resumed across runs. Measured against a local TLS server behind a simulated link (`/tmp` harness, not in the repo): with 50 ms RTT the first request of a run took 55 ms instead of 160 ms (the saving is two round trips, TCP and TLS 1.3), 100 ms RTT 105 ms instead of 310 ms; only the stocked connections benefit, the rest of a burst dials as before. Unit tests in `net/inspect.rs`; not run in a real VM or against the real API. Not done: a CIDR/IP-literal host, WebSockets, response inspection, rate or body limits, a denial turned into a question for the user.
