# Projects, profiles and configuration stores

Projects and scopes, the global system prompt, agent profiles, integrations, VM settings, Claude accounts, variables and secrets. Part of the project notes; the overview is in `CLAUDE.md`.

**Projects** (the unit the user works in; `config/projects.rs`, `config/scope.rs`, UI `Projects.tsx`, `project/ProjectSettings.tsx`): a project owns its **workflows, sessions, agent profiles, images, variables, secrets and injections** and adds **allowed hosts** and a **system prompt** (`project.json`: name, description, system_prompt, allow_hosts). Files live in `<app data>/projects/<id>/` (`project.json`, `workflows/`, `sessions/`, `profiles/`, `images/{specs,built}`, `variables.json`, `secrets.json`, `injections.json`); a project's secret values are in the keyring as `secret:<project>:NAME`. The **global** settings (Settings, tabs named "Global ...") hold the same kinds in the old locations (`variables.json`, `secrets.json`, `injections.json`, `images/`, `network.json`) and are empty by default, except the Claude API hosts (global allowed hosts, default `api.anthropic.com` and `statsig.anthropic.com`) and the built-in `base` image. `Scope` (`Scope::global()` / `Scope::project(id)`) is how a store says which it works on; the commands take `project: Option<String>` (null = global) for variables, secrets, injections, images and network, and `project: String` for profiles (except `profiles_available`, `Option`), workflows, sessions, session/engine commands, triggers and analytics. `profiles_available` takes `project: Option<String>` too (global profiles, variables, secrets, hosts and images only when it is null). The single runs that used to exist (one agent, one prompt, no workflow; page `/runs`, MCP `runs`) were removed on purpose: everything runs as a session. The frontend reads the scope from `useProject()` (null outside a project), so `settings/Images|Secrets|Variables|Injections|Network` are the same components in Settings and in the project's pages. **What a run sees** is the merge of both: variables (`variables::all`, project wins), injections (`injections::available`, project wins by name), secrets (`secrets::secret_value`: the project's, else the global), images (`images::resolve`: the project's, else global, `base` included; a project image may be built on a global one, not the reverse; a project cannot create an image id a global one has), allowed hosts (global + project + profile, `runs::run_vm`; entries may be `${var:NAME}`), the system prompt (global + project + workflow instructions + profile, in that order, `engine/host.rs::prepare`) and agent profiles (see below). Sessions are keyed `<project>/<sid>` in the engine, `session-log` events carry `project`, trigger/cron/webhook nodes are found across all projects (`triggers::find_all`; the webhook listener and its port are global). Deleting a project removes its directory and secrets and is refused while one of its sessions runs or an image builds. Image builds are one at a time across all scopes (`Ref` = scope + id, keyed `<project>/<id>` for logs). Older text below that says "Settings > Images/Secrets/Variables/Injections" or `<app data>/profiles` etc. now means the project's page and directory.

**Global system prompt and global profiles** (asked for by the owner): the **global system prompt** (Settings > LLM, `config/system_prompt.rs`, `system_prompt.json` in the app data dir, commands `system_prompt_get|set`, max 64 KB) goes to every agent first; `system_prompt::with_project` is global + project, and `prepare` adds the workflow's and the profile's after it. **Agent profiles** exist globally (Settings tab "Global agent profiles", `<app data>/profiles`) and per project; `profiles_list|save|delete` take `project: Option<String>` (null = global), `profiles_available(project)` is the project's own plus the global ones (the workflow editor and the session graph use it; `profiles::available`, a project's profile hides a global one with the same id, and a new project profile never takes a global id). A profile may **extend** another (`Profile::extends`, an id): a project's profile can extend a global one or another of the project, a global one only a global one. `profiles::resolve` (at run start, never at save) builds the profile a run uses: the parents' system prompts first then the child's, env merged by name (child wins), `allow_hosts` and `integrations` added together, and `model`, `effort`, `cpus`, `memory_mb`, `image`, `max_*` taken from the child, else the parent (`memory_mb` and `image` are therefore `Option`; `Profile::memory()` and `image_id()` give the defaults 2048 and `base` on a resolved profile). Integrations, injections and leak detection work on the resolved profile, so `Spec.allow_hosts` includes the parents' hosts. Saving checks the parent exists, is not the profile itself and makes no loop (`check_extends`, max depth 8); deleting is refused while another profile extends it (a global one: in any project). `used_images` counts resolved images, global profiles included. Import/export carries `system_prompt.json` (the file's text replaces ours only on overwrite or when ours is empty) and the global `profiles/` directory (already in `SCOPE_DIRS`). Tested: resolution, loops, parent checks, transfer merge; not run in the real app.

**Integrations** (`config/integrations.rs`, UI `settings/Integrations.tsx`, project page `/p/:pid/integrations`, Settings tab "Global integrations", commands `integrations_list|save|delete`, `<scope dir>/integrations.json`): one place to set up a service (Jira, GitHub). It stores only names (`variables`, `secrets`, `injections` it owns) plus `hosts` and `env` (the agent's environment variables); saving writes the variables, secrets (write-only, value optional when already set) and injections into their own stores (`variables::set`, `secrets::set`, `injections::upsert`), where they stay editable, but `check_free` refuses to delete one that an integration of the same scope names (`variables_delete`, `secrets_delete`, `injections_save`). A profile lists `integrations` (names, project's wins over global); at run start `integrations::expand` adds their env (the profile's own wins on a name) and hosts to the profile's, used by `RealHost::run_agent` before `injections::prepare`; a missing integration fails the run. Deleting an integration is refused while a profile of the project uses it (global ones are not checked). No built-in presets (decided: the user defines them; "Duplicate" copies one without the secret values). Not run in the real app.

**VM settings** (`config/vm_settings.rs`, `vm.json`, commands `vm_settings_get|set`, UI section in Settings > General `settings/VmSettings.tsx`): accelerator (`auto|hardware|software`; `hardware` has no TCG fallback and fails when the host has none), default vCPUs for profiles without `cpus`, default memory for *new* profiles (the UI pre-fills it, stored profiles keep theirs), the default size of an agent's work disk (`default_work_disk_mb`, 5120; a profile's `work_disk_mb` overrides it and is inherited through `extends`), VMs at once in the app (read when the app starts, `VmSlots::new`) and per session (`Host::max_vms`), the grace time on top of an agent's timeout, the image script time limit and the builder VM's vCPUs and memory. The network, CPU model, machine type and extra QEMU arguments are deliberately not configurable (they keep the guest sealed and bootable). The export carries only the portable fields (`PORTABLE`: default memory, grace, image script limit), never the hardware-bound ones. Not run in the real app.

**Claude accounts mode** (Settings > LLM, `accounts_mode|accounts_set_mode`, `claude-accounts.json`): `round_robin` (default, each run takes the next ready account) or `drain` (always the first ready account in list order until it rests, then the next).

- `config/secrets.rs`: named secrets in the OS credential store (`keyring`), never in `settings.json`; write-only from the frontend. Linux needs a running Secret Service.

- `config/accounts.rs` (Settings > LLM, `settings/Llm.tsx`; commands `accounts_list|add|set_token|update|wake|remove`): **Claude accounts**, several setup tokens in the keyring (`claude-account:<id>`; the account `default` is the old single-token entry `claude-setup-token`, so nothing to migrate), names and on/off in `<app data>/claude-accounts.json`. `run_vm` takes an account per attempt, **round-robin** over the enabled ones that are not resting (`accounts::pick`; when all rest, the one that wakes first). A failed run whose text says usage/rate limit (or a rejected/expired token) puts that account to rest (`classify` + `rest`: 1 h for a limit, 12 h for a rejected token, in memory only, a new token or "use it again" lifts it) and, **only if the run used no tokens** (`tokens` empty or 0, so no work is repeated), `run_vm` starts again on the next untried account; mid-run limits after real work are not retried (the account still rests for the next runs). Each attempt emits an `{"type":"account","account":<name>}` event (seq 0; the audit export lists them; the token never leaves the app but into that VM's `Bootstrap`). Detection is by matching the failure text, so a message Claude Code words differently will not be caught: check `classify` against the real messages. Untested with real accounts.

- **Variables** (Settings > Variables, `config/variables.rs`, `settings/Variables.tsx`): named values that are not secret, plain text in `<app data>/variables.json`, commands `variables_list|set|delete` (values are returned to the UI, unlike secrets). `${var:NAME}` works in a profile env value (also inside text, `https://${var:HOST}`) and in an injection's rule host, rule path and user name (`injections::resolved` fills them at run start and validates the whole injection then; saving accepts references unchecked). Resolved last in `injections::build`, so a variable's value is never read as another reference; a missing variable fails the run.

- Named secrets (Settings > Secrets, `settings/Secrets.tsx`): values in the keyring (`secret:<NAME>`), names listed in `<app data>/secrets.json` (the store cannot list), commands `secrets_list|set|delete` (write-only, values never returned). A profile env value may contain `${secret:NAME}`; `secrets::resolve_env` fills it in when the run starts (`RealHost::run_agent`; a missing secret fails the run), so the value reaches the VM's environment for `claude` in plain text until credential injection exists. Image env vars are not resolved (baked in plain text). Not checked at save or in `prepare`, only at run start.

- **Agent profiles** (`src-tauri/src/config/profiles.rs`, UI `src/pages/Profiles.tsx`): created by the user in the UI (the app ships none): name, description, system prompt, environment variables, `model` and `effort` (both optional, `None` = Claude Code's default; effort is `low|medium|high|xhigh|max`), `cpus` (vCPUs, `-smp`; `None` = all the host's cores; QEMU cannot cap CPU time, only core count) and `memory_mb` (`-m`, default 2048, minimum 1024) and the image to run on (`image`, default `base`). Nothing is baked into an image: the system prompt and env travel in the `Task`. Every variable has a value, sent as is in the `Task` (there are no run-time-supplied variables); `PATH`, `HOME`, the Claude token etc. are reserved. Stored as `<id>.json` in `<app data>/profiles/`; commands `profiles_list|save|delete`. The system prompt and env travel in the `Task` (`agentd` exports the env for `claude` only and passes `--append-system-prompt`).

**MCP servers in agent profiles** (asked for by the owner; `Profile.mcp_servers`, `config/profiles.rs`, editor `components/McpServersEditor.tsx` in the profile dialog; the profile field is a list of `McpServer {name, kind: stdio|http|sse, command, args, env, url, headers}`): the agent's `claude` gets these MCP servers (the profile's tools, not to be confused with the app's own MCP server below). Streamable HTTP (`http`), SSE (`sse`) and `stdio` (a program started inside the VM as the agent user: it must exist in the image, e.g. `npx` needs Node.js in a custom image; the base image has none). All values (command, args, env, URL, headers) are expanded with `${var:}`, `${secret:}` and `${injection:}` like environment variables: `engine/host.rs` feeds them through `injections::prepare` together with the env (`profiles::mcp_vars`), splits them off and builds the `--mcp-config` JSON (`profiles::mcp_config`), sent as `Task.mcp_config`; `agentd` writes it to a mode 600 file owned by the agent user and passes `--mcp-config` next to the existing `--strict-mcp-config`, so these are the only servers. The host of an `http`/`sse` URL is added to the run's allowed hosts automatically (HTTPS port 443 only; plain HTTP needs `http://host` in the allowed hosts; the allowlist is port 443 only, so a URL with another port will not connect, not checked); IP addresses and URLs with credentials are refused. A literal header value is stored in the profile (and leak detection watches the expanded values like env ones); use `${injection:NAME}` to keep a token out of the VM. `extends` merges the lists by name (the child's server replaces the parent's one). Tested: config building, validation, `agentd.sh` syntax; not run against a real MCP server or a real `claude` (the `--mcp-config` file format with `type` `http`/`sse`/`stdio` comes from Claude Code's docs).

**MCP server** (asked for by the owner; `src-tauri/src/mcp/`, Settings > "MCP (your agent)" `settings/McpSettings.tsx`, commands `mcp_get|set|new_token`): lets the user's *own* agent (Claude Code or any MCP client) configure the app; there is no chat inside the app on purpose. Streamable HTTP, one JSON answer per POST to `http://127.0.0.1:<port>/mcp` (default 7879, off until turned on), bearer token made on first start (`mcp.json` in the app data dir, mode 0600, not in the export; "New token" invalidates clients). Requests with an `Origin` or a non-loopback `Host` are refused. **Two tools only, to save the agent's context**: `read_instructions` (`mcp/instructions.md` = the model of the app and the JSON bodies, then `cli::HELP`) and `execute{command, stdin?}`, a fake CLI `ccaf <resource> <verb> ...` (`mcp/cli.rs`): projects, prompt (global system prompt), profiles, variables, secrets, injections, integrations, images (incl. build), network (add/remove hosts), workflows, sessions (list, get, log, start, continue, message, reply, cancel). Each verb calls the same functions as the UI commands, so validation is the same. Every scoped command needs exactly one of `--global` or `--project <id>` (no implicit default); deletes need `--yes`; structured bodies come as JSON in `stdin`; output is compact JSON, cut at 100 KB; errors are plain text with `isError`. Permissions (Settings > MCP, read per call): `write` (off = read only), `write_global`, `runs` (starting sessions; the key keeps its old name; cancelling is always allowed). **Secrets**: the agent never reads or sets a real value; `secrets create` (and an integration save) stores the placeholder `ccaf-placeholder-set-me` for names that do not exist, never touches an existing one, and `secrets list` marks the placeholders so the agent can tell the user what to fill in (a value that passed through the agent would reach its provider). The server's `initialize` answer carries a short `instructions` text, "Call read_instructions first". **Live refresh**: after any `execute` whose verb is not `list|get|available|log` the backend emits `config-changed`; `Layout.tsx` listens (debounced 150 ms) and bumps a key on the sidebar and the routed page, so everything remounts and reloads, always, with no "changed externally" prompt (unsaved edits in an open editor are dropped on purpose, the owner asked for it). Not exposed: accounts and tokens, VM settings, import/export. Tested: tokenizer, flags, permission switches, host check; also driven by hand against the running app (curl): project, variable, profile with `extends`, image, hosts, workflow, injection, refusals. Starting sessions and runs is wired to the same commands as the UI but was not run against real VMs from MCP; not tested with a real MCP client (Claude Code) yet. **Quick add** (`mcp/quick_add.rs`, command `mcp_quick_add`, buttons in Settings > MCP): writes the URL and token into a client's config; adding again replaces the entry. Claude Code through its CLI (`claude mcp remove` then `add-json ccaf ... --scope user`; needs `claude` on the PATH), Claude Desktop by merging `mcpServers.ccaf` into `claude_desktop_config.json` (config dir + `Claude/`) as an `npx -y mcp-remote` stdio bridge with the token in `env` (its file cannot hold a local HTTP server; needs Node.js and a restart), Codex by merging `[mcp_servers.ccaf]` (`url`, `http_headers.Authorization`) into `$CODEX_HOME/config.toml` (default `~/.codex`) with `toml_edit`, which keeps comments and other tables. A file that does not parse is left alone with an error; the first change copies the file to `<name>.ccaf-backup`. Tested: both merges and the backup; the real clients were not run (the formats come from their docs).
