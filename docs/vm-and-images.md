# VM, QEMU and images

QEMU bundling, confinement, the base image, custom images, tool docs, the builder VM, starting agents and fast boot. Part of the project notes; the overview is in `CLAUDE.md`.

**Detailed agent logs** (setting `debug_logs` in VM settings, Settings > General > Virtual machines, default off; asked for by the owner so their agent can debug runs; logs of the agent itself, not of the VM): the session log already holds every `claude` stream-json line (messages, tool calls and results) as `agent` entries, up to `MAX_EVENT`. With the setting on, `Task.debug` makes `agentd` run `claude` with `--debug-file` (a `mktemp` file owned by the agent user) and, before the final, send an `agent_debug` event (seq 0: exit code, the last 20 KB of `claude`'s stderr, the last 60 KB of its debug log). MCP: `ccaf sessions log <id> --project P --agent [--node ID] [--last N]` includes the `agent` entries, which the plain log drops, with every string clipped (3000 characters, 20000 with the setting on). It needs an image with the new `agentd` (the base is rebuilt as stale). Not run against a real VM yet. Not exposed through MCP: switching the setting.\n\n**VM process confinement** (`vm/confine.rs`, `machine::confine|confine_started`, setting `confine` in VM settings, default on; asked for by the owner): the guest is the first boundary, this is the second: whoever escapes it through a bug in QEMU lands in the QEMU process, which runs as the user, so that process is boxed in before it starts (`confine::apply(cmd, Plan)` on the std `Command` in `runs.rs` and `images::launch`; the QEMU of `qemu-img` and `qemu_version` is not). **Linux**: Landlock (raw syscalls, set in `pre_exec` from a ruleset built in the parent so the child does only async-signal-safe calls): read on QEMU's own tree (`qemu_root`: needs `share/qemu`, so a system QEMU in `/usr/bin` only gets its own file), the library folders (also executable) and `/etc /proc /sys /run /usr/share`, a few device nodes (`/dev/kvm`...), the shipped kernel dir, each disk with its whole qcow2 backing chain (`backing_chain` reads the headers), write on the VM's own folder only; no program outside QEMU's tree and the library folders can be run, so no shell after an escape; plus `RLIMIT_CORE=0` (no guest memory in core dumps), `RLIMIT_FSIZE` 64 GiB, no-new-privs, and QEMU's seccomp filter `-sandbox on,obsolete=deny,elevateprivileges=deny,spawn=deny,resourcecontrol=deny` when the binary has it (probed with `-sandbox on -version`, once per binary). **Network** (agent VMs only, Landlock ABI 4 = kernel 6.7): TCP `connect` and `bind` are handled and no port may be connected to (`Limits::connect_ports` is an empty list: the VM has no NIC and QEMU serves its sockets, it dials nothing), so an escape cannot reach the LAN or the app's other local ports (webhook listener...). Builders need the internet and get no network rule. **Limits** (`Limits`, Linux): `RLIMIT_DATA` = guest memory + `MEM_HEADROOM_MB` (2048; measured with the bundled QEMU under software emulation, the worst case because of its 1 GiB translation buffer: 1 GiB of guest needs ~2.2 GiB, 2 GiB with 4 vCPUs ~3.3 GiB, 3 GiB with 8 vCPUs under 5 GiB; a too-tight limit shows as `failed to allocate` in QEMU's stderr, and the `confine` setting turns all of this off) for agent VMs and builders, and `RLIMIT_CPU` = (timeout + grace) x (cores + 1) + 120 s for agent VMs only, a backstop for a VM that outlives the app. Not cgroups (`systemd-run --user` was not used: no systemd user manager is guaranteed, and a process it starts would not inherit the Landlock rules). Each part is skipped with a log line when the kernel or the binary lacks it. **macOS**: `sandbox-exec -p <profile>` around QEMU (allow default, deny fork/exec except QEMU, deny the home folder except what the VM uses; last rule wins), probed once with `--version`, otherwise VMs run unconfined with a warning. **Windows**: `after_spawn` puts the process in a job object (one process, kill on close, UI restrictions); handles of finished VMs are closed on the next spawn. Tested on Linux: unit tests in `confine.rs` (chain, Landlock on a child, program blocked) and the real bundled QEMU booting the plain image and a full fake-token agent run under Landlock + `-sandbox` (x86_64, TCG; `Seccomp: 2` on the live process; a kernel outside the plan is refused). The macOS and Windows code only type-checks (`cargo check --target aarch64-apple-darwin|x86_64-pc-windows-gnu`); it has never run, and the macOS profile is a guess to verify on a Mac. Tested with the real bundled QEMU (x86_64, TCG) under the whole set: (measured when the VM still had the `guestfwd` NIC: the allowed port worked and another one made QEMU refuse to start; the agent VM now needs no allowed port.) Not done: cgroup memory/CPU caps, the network rule and the limits on macOS and Windows (not tried; the macOS profile is a guess already), an aarch64 run, a restricted token on Windows, confining `qemu-img`.

- `vm/qemu.rs`: `command(app, program)` builds a `Command` for any QEMU binary. It uses the bundled tree at `<resource_dir>/qemu/{bin,lib,share/qemu}` (adding `-L share/qemu` for `qemu-system-*`) and falls back to PATH if the build shipped no QEMU. On Windows it sets `CREATE_NO_WINDOW`. Spawn all QEMU processes through it.

**QEMU bundling pipeline** (spans several files)
- The built QEMU trees are committed as `vendor/qemu/qemu-<target-triple>.tar.gz` (linux x86_64 and aarch64, macOS x86_64 and aarch64, windows x86_64; checksums in `SHA256SUMS`), so no CI or network is involved.
- `scripts/qemu/fetch.mjs` unpacks the archive for the target triple (`$TAURI_ENV_TARGET_TRIPLE`, else the host) and stamps `.version`. `tauri.conf.json` bundles `resources/qemu/` as `qemu/`. Everything in that directory except its README is git-ignored.
- The Linux builds (x86_64, aarch64) have **seccomp** (`--enable-seccomp`, `libseccomp.so.2` ships in `lib/`), so `-sandbox` works there; the recipe is commit `575dfb4` (see `vendor/qemu/README.md`). Keep `--enable-seccomp` when rebuilding them: `vm/confine.rs` probes for it and runs without it, with a warning.
- Upgrading QEMU means building it from source on each OS (Linux builds should use an old glibc, e.g. Ubuntu 22.04; macOS needs the HVF entitlement and ad-hoc signing; the old build script is in git history, commit 932a4de), replacing the archives in `vendor/qemu`, and updating `SHA256SUMS`.

**Agent VM base image** (`scripts/images/`)
- The base image is plain Alpine (`alpine-base` only, no kernel or modules in it, `main` and `community` repos, one ext4 root of 8G with no partition table and no bootloader, DHCP on eth0, empty root password and a serial login for the builder, no SSH, nothing else). It is two files per arch in `vendor/images`: `alpine-<x86_64|aarch64>.qcow2` (~5 MB, qcow2 compressed with zlib: the bundled QEMU is built without zstd), and `.vmlinuz`, a **custom kernel** (6.18 longterm from kernel.org, `make tinyconfig` plus only what the guest uses: virtio PCI block/net/serial/rng, ext4, the console UART, ACPI or PSCI for poweroff, RTC, IPv6/PACKET, Yama; everything built in, no modules, no initramfs, `PANIC_TIMEOUT=-1`; x86_64 is a bzImage with LZ4, 4.2 MB, arm64 a raw `Image`, 6.5 MB; hardened: KASLR, strong stack protector, hardened usercopy, FORTIFY_SOURCE, slab freelist random/hardened, init_on_alloc, kstack offset randomisation, `mmap_min_addr` 65536, `io_uring` off, high-res timers on; not enabled: CPU mitigations, which the agent boot args turn off anyway), which QEMU boots directly (`-kernel`, `root=/dev/vda`). The kernel recipe (config fragments `common|x86_64|aarch64.config`, `build.sh`, a CI workflow) is not in the tree any more, only in git history at commit `598aef4` (with the hardening options; the hashes given here earlier did not exist) plus these lines added to `common.config` for the shared folder (9P over a file descriptor, no TCP or virtio-9p; the kernels in `vendor/images` were rebuilt with them by a throwaway CI workflow on 2026-11-03, +65 KB on x86_64, +72 KB on arm64): `CONFIG_NETWORK_FILESYSTEMS=y`, `CONFIG_NET_9P=y`, `CONFIG_NET_9P_FD=y`, `CONFIG_9P_FS=y` (`kernel/`, `.github/workflows/kernel.yml`); to change the kernel, restore those, build natively per arch on GitHub Actions and replace the two `.vmlinuz` files. Not covered by the config on purpose: namespaces, cgroups, USB, graphics, sound, other filesystems (except 9P, see above), netfilter, loop devices (an image script that needs one fails), so there is no BIOS/UEFI/bootloader step and both arches boot the same way. Made by `scripts/images/build-plain.sh <arch> <out>` (needs root, curl, e2fsprogs, qemu-img; natively per arch: x86_64 and aarch64 were built by a throwaway GitHub Actions workflow on `ubuntu-22.04` and `ubuntu-22.04-arm`, which also booted each to the login prompt; the workflow and its runs were deleted; Alpine branch in `scripts/images/version.json`). Redoing the images means running that script on both arches again and replacing the two disks (the kernel is separate). The root has no kernel or modules, so an image script that installs a kernel package changes nothing (the shipped kernel always boots).
- Claude Code and `agentd` are **not** in the image yet. The app is meant to install them in a builder VM on the user's machine (Claude Code from the official installer, `agentd` is the script `resources/agentd/agentd.sh`, the same for both arches; also `apk add jq setpriv` (Alpine's own `setpriv` package: busybox's applet lacks `--reuid`, and `setup.sh` checks the real one works), no git), cache the result as the real base, and rebuild when the app updates. Not built yet. The old in-image installer (Claude Code, the `agent` user, the `agentd` OpenRC service) is `scripts/images/provision.sh` in commit 932a4de, the model for that step. The builder VM also needs a way to run commands in the plain image (planned: a first-boot hook that mounts a setup disk and runs its script).
- **Images** (`src-tauri/src/vm/images.rs`, UI Settings > Images, `settings/Images.tsx`): what agents run on, managed apart from agent profiles. The **base** image (plain Alpine + agentd + Claude Code + ripgrep, `resources/agentd/setup.sh`) is built in and not editable; it is built at startup when missing or stale and on Rebuild. **Custom** images are user-made: name, description, a parent (`base` or another custom image, no cycles), environment variables baked into the image and a shell script that runs as root in a builder VM on top of the finished parent. Files in `<app data>/images/`: `specs/<id>.json` (custom definitions), `built/<id>.qcow2` + `built/<id>.json` (standalone flattened disk + stamp). Stamp: base = hash of `setup.sh`, `agentd.sh`, `agentd.initd` and the plain image's size; custom = hash of the parent's stamp and the script, so a new base, a rebuilt parent (down the chain) or an edited script makes it "stale" (kept usable, rebuilt on request, one build at a time). Saving a custom image starts its build at once (if its parent is built and no other build runs; otherwise it waits for the build button). Baked variables are `export NAME='value'` lines appended to `/etc/conf.d/agentd` (OpenRC sources it, so agentd and the `claude` it runs inherit them; children append to their parent's, later wins; agentd itself knows nothing about them; stored in plain text, no secrets; also part of the stamp). **Starter images and profiles** (first-start welcome dialog, `src/components/Welcome.tsx`, pref `welcomed`): asked once; on yes, `provision_starters` creates the images `manager` (on the base: `jtk` (Jira CLI) from `open-cli-collective/atlassian-cli`, binary in `/usr/local/bin`; the repo holds several tools, so the script picks the newest `jtk-v*` tag from the release list; it reads `ATLASSIAN_URL`, `ATLASSIAN_EMAIL` and `JIRA_API_TOKEN` from the environment, which the demo profiles set, the token as `${injection:JIRA}`, no config file; not verified in a real build), `developer` (on `manager`: git, github-cli, python3, nodejs, npm, a system-wide git identity) and `qa` (on `manager`: Alpine's chromium + the `agent-browser` musl binary from its latest GitHub release, no Node; `AGENT_BROWSER_EXECUTABLE_PATH` and `AGENT_BROWSER_ARGS` (`--no-sandbox`) baked; not verified in a real build) and the profiles `developer` and `qa` on them. The demo content also creates three secrets (`GITHUB_TOKEN`, `GITHUB_READONLY_TOKEN`, `JIRA_TOKEN`; value `dummy`, `secrets::provision_demo`) and one injection each (`GITHUB[_READONLY]` is Basic `x-access-token` on github.com and api.github.com, `JIRA` is Basic on `${var:ATLASSIAN_HOST}` with `${var:ATLASSIAN_EMAIL}` (variables, Settings > Variables; placeholders to edit), path `/rest/*`). Read-only (GitHub) is the token's scope, not a proxy rule (git, `gh` and Jira search read with POST). The demo also defines three **integrations** (`integrations:` in `demo.yaml`, `integrations::provision_demo`, `integrations_reset_demo`, a reset button on the Integrations page): `Jira` (hosts `${var:ATLASSIAN_HOST}` and `api.media.atlassian.com`, env `JIRA_API_TOKEN`, `ATLASSIAN_URL`, `ATLASSIAN_EMAIL`, the variables, secret and injection above), `GitHub read-write` (`GH_TOKEN` = `GITHUB`) and `GitHub read-only` (`GH_TOKEN` = `GITHUB_READONLY`), and the profiles list them in `integrations` instead of repeating env and hosts (they keep only the npm/pip/`*.githubusercontent.com` hosts); the variables, secrets and injections stay in their own lists and pages, so an integration cannot be saved over them without them. The older description of how profiles get them follows. Profiles got them through their `env` in the demo file: `GH_TOKEN` is `GITHUB` for the developer and the reviewer (who also approves and merges) and `GITHUB_READONLY` for architect and qa; `JIRA_API_TOKEN` (one token, no read-only variant; plus `ATLASSIAN_URL` = `https://${var:ATLASSIAN_HOST}` and `ATLASSIAN_EMAIL` = `${var:ATLASSIAN_EMAIL}`) go to project manager, business analyst, architect, developer, reviewer and qa. The starter images carry their tools' docs (see Tool docs below): `manager` the `jtk` help pages, `qa` `agent-browser --help`, written from the tools' own output at build time (not tested in a VM). Developer and reviewer share one GitHub token (one account), so GitHub refuses the reviewer's approve/request-changes on the developer's pull request; the reviewer's prompt says to leave an APPROVED / CHANGES REQUESTED comment instead. Jira has one token for all, so "only the project manager moves tickets" is a rule in the prompts, not enforced. Untested with a real GitHub: that the API accepts Basic with a token as the password through the proxy. **All the demo content (variables, secrets, injections, images, profiles, the standard workflow) is defined in one file, `src-tauri/demo/demo.yaml`** (image scripts are `src-tauri/demo/*.sh`, named by `script:` and compiled in by `demo.rs`, which parses the file once; a mistake panics and `cargo test` catches it, with cross-reference checks: profiles' images, nodes' profiles, injections' secrets); the modules' `provision_*` functions take their part from `demo::{variables,secrets,injections,images,profiles,workflow}`, so changing the demo means editing that file only. They are ordinary custom images and profiles, existing ids are left alone, and the user can edit or delete them. The images build after the base like any child. On an error the dialog comes back on the next start. It also creates the profiles `orchestrator`, `project-manager`, `business-analyst` (both on the `manager` image), `architect`, `reviewer` (on the `developer` image) and the standard workflow (see Workflow). **Reset to demo content**: a small button (`ResetDemoButton.tsx`, with a confirmation that says what is lost) on Agent profiles and on the Settings tabs Images, Secrets, Variables and Injections, each separate (`profiles|images|secrets|variables|injections_reset_demo`, the `provision_*` functions with `reset = true`): the demo items are written again over what is there (secrets get `dummy`, variables their placeholders, so real values are lost), other items are left alone; for images the ones then missing or stale are built, refused while a build runs. Commands `images_list|save|delete|build` (a deleted image cannot be in use by a profile or be another image's parent). When an image finishes building, the images built directly on it are queued and built next, and theirs after each of them (a chain reaction, one build at a time, state `queued` in the UI; a failed build queues nothing; deleting an image drops it from the queue). A custom image cannot be built (or listed as buildable, `can_build`) until its parent is built. Build output goes through a pipe with `TERM=dumb` (`builder::script_cmd`) so installers print plain lines instead of cursor-addressed redraws. Stale custom images are rebuilt at startup (`ensure_base`: the base if it is stale, otherwise the stale custom images whose parent is up to date; the rest follow by the chain reaction), and a run boots its profile's image.
- **Tool docs** (`Spec.docs`, UI Settings > Images, section "Tool docs for the system prompt"): a list of entries, each `text` (written as is: titles, short advice) or `command` (run in the builder VM after the image script with `NO_COLOR=1`, `sh -c`, stdout and stderr in a code block, a failing command does not fail the build). `docs_script` in `vm/images.rs` turns them into a shell script that writes `/usr/share/ccaf/tools/NNN-<image>.md` (NNN = number of files already there + 1, so a parent's come first; children inherit the parent's files because the disk is flattened from it). `agentd` appends every `*.md` in that directory (`--tools-dir`, in name order, capped at 40 KB) to the end of the system prompt under `# Command-line tools in this environment`, after the workflow instructions and the profile's prompt. Part of the stamp only when there are entries. The text is baked in the image, so editing it means a rebuild, and it is sent with every run (keep it short).

- **Starting agents** (`src-tauri/src/vm/runs.rs`): `run_vm(app, run_id, image, identity, task, cancel, on_msg)` makes a throwaway qcow2 overlay of the image under `<app data>/runs/tmp/<run>/`, boots it with `images::machine` (shared with the builder: accel with tcg fallback, `-cpu max`, `-no-reboot`, `-nodefaults`, the shipped kernel booted directly (`images::boot_args`; agent VMs: silent, `init=/sbin/ccaf-init`, no console; builders: serial console and the stock init), a virtio NIC, at most 4 vCPUs when the profile gives none, the disk through `images::drive_arg` with `cache=unsafe` since overlays are throwaway; the caller adds `-nic`: builders get open `user` networking, runs a sealed card, see Egress control) plus `-action panic=exit-failure`, the virtio-serial `agent` port on a `Serial::named` socket (named pipe on Windows, untested), connects, and hands the channel to `agent::drive` with the `Bootstrap` (identity, token from the keyring, `tunnel` keys) and the `Task`. Before QEMU it starts a `tunnel::Tunnel` with the run's rules (the global list from `network::current` plus the profile's `allow_hosts`, `Spec.allow_hosts`); the proxy's log lines reach `on_msg` (and the run and session logs) as events with `seq` 0 and `{"type":"egress","text":...}`, which the UI digests ignore. It always ends with exactly one `Final`: the agent's, or a synthesized `failed` one when the stream ends / QEMU dies (with the tail of QEMU's stderr), the deadline (task timeout + 300 s grace) passes (VM killed) or the run is cancelled. Overlay and VM are removed afterwards. Errors that stop a VM from starting (no token, image not built) are `Err`. The **identity** is a SPIFFE-style label, `spiffe://ccaf.local/<kind>/<id>/.../run/<run>` (`runs::identity`), sent as `Bootstrap.id`, exported to `claude` as `CCAF_AGENT_ID` and written in the log; it is not a credential and nothing verifies it, the channel is the authentication. The `Task` now carries the profile's `system_prompt` (`--append-system-prompt`) and `env` (exported for `claude` only; `agentd` drops invalid names and the reserved ones, values are shell-quoted by jq). Only the workflow engine starts agents (`RealHost::run_agent`); the single runs that had their own commands, page and log files were removed. Verified on x86_64 Linux with KVM: `cargo test boots_an_agent_vm -- --ignored --nocapture` boots the built base image (`CCAF_BASE=<path>` for another one) with a fake token: `agentd` runs as a service, the relay opens, `claude` reaches the API through the egress proxy (401) and the log shows `api.anthropic.com:443 allowed`, the final arrives, the VM powers off (~8 s from QEMU spawn to exit with the fake token, of which about 3 s is the guest booting and `claude` starting; was ~20 s before the changes in Fast boot below; needs an image built with the current `setup.sh`, i.e. with `ccaf-relay`, e.g. `CCAF_KEEP_BASE=<path> cargo test builds_the_base_image -- --ignored`). Not verified: a run with a real token, aarch64, macOS, Windows. Not built: (the engine that calls this per step is `workflow/engine/`, which also caps the VMs: 4 per session and 8 in the app, `VmSlots`).
- **Machine half and app half of a run** (`vm/launch.rs`; the first step towards running VMs on other computers, asked for by the owner, who runs the full app, GUI or `--headless`, on every node): `launch(app, LaunchSpec, progress)` makes the overlay and the work disk, spawns QEMU (confined) and returns `Launched { agent, net, shared, vm }`: three `Box<dyn Stream>` (the virtio-serial ports) and a `Vm` handle (`wait`, `stats`, `err_tail`, `end` = kill and remove the run folder; an enum, today only `Local`). Everything else stays in `runs::boot_and_drive`, the app half: the egress proxy with its CA and the real token, the tunnel, the 9P server on the shared folder's contents, `agent::drive`, the deadline, the data budget and the events. Only those streams and the handle have to cross a network for a remote node; secrets and policy never leave the app. `LaunchError::Setup` is a hard `Err` (no image, no QEMU), `Failed` a `failed` final carrying QEMU's own words. Since the split the proxy is made while the VM boots (before, the overlay was copied in parallel and the proxy finished before QEMU spawned). Checked with a real session on the base image (VM states, tunnel, egress, stats, net totals, final, `off`).
- **Nodes: VMs on other computers** (`src-tauri/src/nodes/`, Settings > Nodes `settings/NodesSettings.tsx`; asked for by the owner, who runs the full app, with a GUI, on every computer, and trusts all nodes): the app that runs a session (the *hub*) starts a run's VM on another computer running this same app (a *node*). The seam is `launch::launch_on(target)`: `Target::Local` is the code above, `Target::Node` is `nodes/client.rs::launch`, which returns the same `Launched` (three streams and a `Vm::Remote` handle), so everything on the app half (proxy with the real token and injections, tunnel, 9P server on the shared folder, `drive`, deadline, budget, journal and resume) is unchanged and secrets never leave the hub. **Protocol** (`proto.rs`): every connection is TLS (`tls.rs`) and starts with one JSON line `Hello {proto, key, op}`, answered by one `Reply` line; `ping`, `image`, `vm` (the connection stays as the VM's control channel: node sends `stats` every 2 s and `exit`, hub sends `kill`; 15 s of silence = node lost), `attach {vm, port}` (afterwards the raw bytes of the `agent`, `net` or `shared` port, `copy_bidirectional` to QEMU's socket), `drop {prefix}`. Four connections per VM, no multiplexer; lines are read a byte at a time so raw bytes can follow. **Trust**: the node has a self-signed certificate (`node-cert.json`), the hub pins its SHA-256 fingerprint when the node is added (Settings > Nodes > Add: the page connects without sending anything secret, shows the fingerprint to compare with the node's own page, then asks to trust it; `nodes_probe`, `nodes_save`, which also checks the key), and the node's key (`node.json`, generated once, constant-time compared, a wrong one is delayed 0.5 s) authorizes the hub. **Node side** (`server.rs`; off by default, Settings > Nodes > "Accept VMs from other computers" or `--node`; default `0.0.0.0:7881`; commands `node_get|set|new_key`): `vm` runs `launch::launch` locally, so confinement, overlays and the work disk are the usual ones; the VM ends on `kill`, when the control connection breaks, or `timeout + grace + 180 s` after it started. Images (`<data>/node/images/<hash of the hub path>-<size>-<mtime>.qcow2`) are sent by the hub the first time a version is needed (`image` op, one upload per image and node at a time, older versions removed); built images are flattened, so one file is enough. Work disks live in `<data>/node/work/<key>.qcow2`, `key = <project>/<session>/<node id>`. **Hub side**: `nodes.json` (this computer runs VMs: default on; nodes: name, `host:port`, key, fingerprint, enabled, slots), checked every 10 s with `ping` (version, arch, os; a node of another architecture is shown as unusable, images are per-arch). **Scheduler** (`nodes::place`, called by `RealHost::run_agent` instead of the old single semaphore): one semaphore per target (this computer = `VmSlots`, `max_vms`; a node = its `slots`), the emptiest share first, waits for a slot, cancel ends the wait. An agent's work disk is **pinned** to the computer of its first run (`node-pins.json`: key to `local` or node id; a node that is gone or offline fails the run with a message instead of starting with a blank disk); `nodes::forget` drops pins and tells the nodes to delete the disks when a session or project is deleted. A run on a node logs `{"type":"node","node":<name>}` after the `account` event. **Not done**: nodes of another architecture or Windows nodes (Unix sockets; untested), moving a work disk, the node's own slot limit for hub VMs (the hub's `slots` is the only cap), a progress indication for the image upload, a node running the proxy (all agent traffic leaves from the hub), exporting the node list. **Tested** on one machine with two instances (a node with its own data dir through `XDG_DATA_HOME`): pairing (wrong key and wrong certificate refused), the image upload, a full run on the node (states, stats, egress through the hub's proxy, the agent's answer; with a fake token, so the API said 401), cancel stopping QEMU on the node, work disk pin, disk deleted with the session; unit tests for the wire format, the pinning and the address check. Not tested: two real computers, a node that disappears mid-run, a large image over a slow link, the macOS and Windows builds.

- `src-tauri/src/vm/builder.rs` is the builder VM driver: it boots an overlay of the source image with the console on a unix socket (`-serial unix:...`), logs in as root (the plain image has an empty root password and no SSH), switches the tty to no echo / no XON-XOFF, sends files as base64 here-documents (`put`), runs commands with a `DONE-<nonce> <exit>` marker (`run`, streaming cleaned output lines), then `poweroff`, and the app flattens with `qemu-img convert` (not compressed: reads at boot stay cheap). Builder VMs use `-accel kvm|hvf|whpx -accel tcg -cpu max` (Claude Code's Bun needs SSE4.2, so never the default CPU); on aarch64 without KVM/HVF (`machine::hw_accel`) it is `-accel tcg -cpu max,pauth-impdef=on`, since under hvf/kvm `max` is the host CPU and QEMU refuses `pauth-impdef` (it then exits at once, seen as a refused console connection). They have no virtio agent port, and `agentd.initd` refuses to start without `/dev/virtio-ports/agent`, so the agent does not run (and power the VM off) while a custom image is built. Tests: console driver on the plain image (Linux, needs KVM), and `cargo test builds_the_base_image -- --ignored --nocapture` runs the real base setup (network, ~30 s with KVM). Verified on x86_64 Linux only: the base setup succeeds, `claude --version` works. Not verified: the whole flow through the app (poweroff, convert, rename), a custom image build, a boot of the finished image with agentd as a service, aarch64 (the image boots to the login prompt under TCG in CI; nothing else ran there), macOS, and Windows (the console is a named pipe there, `-serial pipe:ccaf-console-…`, QEMU adds the `\\.\pipe\` prefix itself, created by QEMU and opened with tokio's `named_pipe` client; it type-checks for `x86_64-pc-windows-gnu` but has never run; the builder also asks for `whpx`, which needs the Windows Hypervisor Platform feature, else it falls back to very slow `tcg`).

- The plain image ships inside the app: `scripts/images/fetch.mjs` (`pnpm images:fetch [--required]`, run by the dev and build before-commands) copies `alpine-<arch>.qcow2` for the target (aarch64 targets get aarch64, everything else x86_64) from `vendor/images/` into `src-tauri/resources/images/` (git-ignored), and `tauri.conf.json` bundles it as `images/`.
- Custom images are valid only for the base they were built from (see the stamp above). After an app update with a new base they show "out of date" and keep working until rebuilt. They are built standalone (flattened), not as overlays: the bundled plain image sits in the install directory, which an update replaces and an AppImage mounts at a different path each run, so a backing file would break.
- There is no image or QEMU build in CI: both are committed (`vendor/qemu`, `vendor/images`).
- Image/app version drift: `agentd.sh` is bundled with the app and installed into the base the app builds, so the app and its `agentd` always match; there is no protocol version number.
- The image has no SSH at all (the egress path is `ccaf-relay` over a virtio-serial port, see Egress control), and the setup step must fail if an SSH package, sudo or doas is present
- Boot agents from a throwaway `qemu-img create -b` overlay, never from the base image itself.

**Work disk** (agents of a session; asked for by the owner; not run against a real VM yet): `/home/agent/work` is a disk that outlives the VM. `RealHost::run_agent` gives each workflow node a sparse qcow2, `sessions/<sid>.work/<node>.qcow2` (`store::work_disk_path`, the node id written as `[a-z0-9-]` and `_xx`), made with `qemu-img create` on the node's first run in the session at the profile's `work_disk_mb` or the global `default_work_disk_mb` (the size is fixed then; a later setting does not resize it). It is the VM's second virtio disk (`persistent_drive_arg`, `cache=writeback`, so the guest's flushes reach the file), `/dev/vdb`; `ccaf-init` passes `--work-dev` to `agentd` when it exists. `agentd` formats a blank disk (first 64 KiB all zeros; `mkfs.ext4`, so `e2fsprogs` is in `setup.sh`: images need a rebuild) and mounts it (`noatime,nosuid,nodev,discard`) on the workspace, chowns only the top folder, and before powering off runs `sync` and `umount`. A disk with data that does not mount fails the run; it is never reformatted. One lock per disk (`runs::disk_lock`): runs of the same node in a session do not overlap. Deleting a session deletes `sessions/<sid>.work/`. The confinement plan makes the disk's folder writable. Files deleted in the guest do not shrink the qcow2 (`discard` is passed but not checked against this kernel). `agentd` reports `{"type":"disk","size_mb","used_mb"}` (seq 0) after mounting and before the final; the session view shows it as a bar per run (`DiskMeter`). **Shared folder** (agents of a session; asked for by the owner; `vm/shared.rs`): `/home/agent/shared`, the same folder for every agent of the session (`sessions/<sid>.shared/`, deleted with the session), read-write, live. The app is the file server: a **9P2000.L server in Rust** answers on a third virtio-serial port `shared` of each VM (QEMU's own `-virtfs` is not in the bundled builds, is POSIX-only and would need QEMU rebuilt; this way no host file system is handed to QEMU and it works the same on Windows). In the guest the kernel's 9p client (`trans=fd`, built into the shipped kernels, see Agent VM base image) cannot write to a virtio port directly (kernel 6.18: "kernel write not supported for file /vport0p1"), so `agentd` (`--shared-dev`, given by `ccaf-init` when `/dev/virtio-ports/shared` exists) puts two `cat`s between the port and a pair of fifos, each `cat` opening the fifo by name (the kernel makes the descriptors it is given non-blocking, which stops a `cat` that shares them), mounts `-o trans=fd,rfdno,wfdno,version=9p2000.L,aname=<uid>:<gid>,msize=262144,nosuid,nodev`, then closes the descriptors so `claude` does not inherit them. Server rules, the same on every host: paths are name lists below the root (`..` stops at the root), symlinks are never followed or made (nor hard links, device nodes, xattrs), every file belongs to the agent user (ids from `aname`), names that some host cannot hold are refused (`<>:"\|?*`, control characters, Windows device names, trailing dot or space, over 255 bytes) and so is a name that differs from an existing one only in case, locks always succeed, requests are answered one at a time. The executable bit is kept where the host has one (Unix) and is lost on Windows (the planned index for it was not built). One quota for the whole folder (`shared_quota_mb`, 2048), shared by all the session's VMs running together (`quota_for`), counted by the server (writes that grow, truncation, unlink, replacing rename); a write past it fails with ENOSPC. Writes from two agents to the same file are last-writer-wins at the byte level, no coordination. Tested: the server against a hand-made client (round trip, names, quota across two servers, directories and rename, symlinks), and by hand a Linux guest on the x86_64 kernel under TCG (mount, list, read, write, mkdir, mv, rm, refusals) with a throwaway Python server and with the Rust one (`serve_for_a_vm`, ignored); not yet through a real agent run (the image needs rebuilding for the new `agentd`), not on aarch64, not on Windows or macOS hosts for the file side (the macOS host ran the manual test). **Files tab** (session view, `pages/session/Files.tsx`, commands `workflow/files.rs` `shared_list|mkdir|delete|upload|download|reveal`, operations in `vm/shared.rs` `list|make_dir|remove|import_file|export`): the user sees and changes the same folder live (refreshed every 3 s). Download asks where to save (a folder is copied into a chosen folder, symlinks skipped), upload picks files through the native dialog (no overwrite, same name rules and the same quota as the agents, which the server and the tab share through `quota_for`), new folder, delete (with confirmation) and "show in file manager". There is no "open": what an agent wrote is untrusted, so files are only saved or looked at in the file manager. Paths from the UI are plain names, no `..`, no backslash, and no folder on the way may be a symlink. The session's prompts tell agents that whatever they want to give the user goes in `/home/agent/shared` with its path in the answer. The work disk has no tab: it is an ext4 disk inside a qcow2 that the host cannot read (reading it without a VM would need an ext4 reader on a raw copy; not built). Nothing else is shared between agents.

**Fast boot** (agent VMs; builders keep the stock boot): QEMU boots the shipped kernel directly (see Agent VM base image) with `init=/sbin/ccaf-init` (`resources/agentd/ccaf-init.sh`, installed by `setup.sh`, part of the base stamp together with the kernel size). It is PID 1 and does only: mount proc (`hidepid=2`), sys, dev, devpts, tmpfs for /run, /tmp and /dev/shm, `ptrace_scope=2` (if the kernel has Yama), mdev for `/dev/virtio-ports/agent`, no network but loopback (the relay, see Egress control), sources `/etc/conf.d/agentd` (baked image variables), runs `agentd --run-as agent --poweroff` in the foreground, and powers off if it returns. OpenRC stays installed (packages and image scripts may use it) but agent runs never start it. `agentd` ends with `poweroff -f` (the disk is a throwaway overlay). The NIC is `virtio-net-pci` (built into the kernel, which has no other NIC driver), the disk has `cache=unsafe`, the machine has `-nodefaults` (no VGA, CD-ROM, floppy), the kernel runs `quiet`, built images are not compressed (`vm/images.rs` converts without `-c`) and a profile without `cpus` gets at most 4 vCPUs. `setup.sh` also strips every setuid/setgid bit and fails if one is left (busybox `su` would accept the plain image's empty root password), so the agent cannot become root. `cargo test boots_an_agent_vm` prints `TIMING` lines. `ccaf-init` also reads `claude`, `jq`, `rg` and the libraries into the page cache in the background while agentd waits for the app. Agent kernels also get `random.trust_cpu=on mitigations=off noresume raid=noautodetect` (x86_64 also `i8042.noaux i8042.nokbd tsc=reliable no_timer_check`). On the host `runs.rs` makes the overlay by copying a template made once per image version (`runs/overlays/`), in parallel with starting the tunnel, and reads the image and kernel into the cache once per process. None of this has been timed yet. The custom kernel is done (no initramfs, no module loading); measured only under software emulation: boot to `agentd` up in ~4.5 s guest time with TCG, x86_64 end to end with a fake token (`claude` reaches the API, 401, powers off), aarch64 only booted to a shell-level check. `rootflags=noatime` must not be passed: with no initramfs the kernel mounts root itself and ext4 rejects it, so `ccaf-init` remounts `/` with `noatime` instead (checked: the remount works). The root has **no journal**, so `data=writeback` is refused (kernel panic, tried) and `barrier=0` would do nothing. Agent kernels also get `rcupdate.rcu_expedited=1` (accepted by the kernel, effect not timed). On the host, `boot_and_drive` copies the overlay (off the executor, `spawn_blocking`) while the run's CA is made and the proxy and tunnel start; `Proxy::warm` also makes the certificates of the inspected exact hosts ahead of the guest's first handshake (`Inspector::pregenerate`). Network tuning: `TCP_NODELAY` on the accepted QEMU stream and on every dialed upstream connection, 64 KiB copy buffers for tunnelled connections, (the SSH tuning is gone with SSH; yamux uses its default 256 KiB window per stream, not tuned); none of it timed: check with `cargo test boots_an_agent_vm -- --ignored` on a machine with KVM and a rebuilt base image. Not done: microvm, snapshots or a pool of pre-booted VMs (declined), checking that an image script did not upgrade the kernel, an aarch64 `arm64.nopauth` for software emulation (needs a measurement).
