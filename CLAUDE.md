# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CC Agent Flows: a Tauri 2 desktop app (React 19 + TypeScript frontend, Rust backend) for running multi-agent, dynamic, end-to-end delivery pipelines built on Claude Code. Design goals:

- Agents run fully sandboxed inside QEMU VMs.
- Authentication uses a Claude Code personal subscription (setup tokens), not API keys.

Current state: the shell is in place (layout, settings, i18n, theming, auto-update, bundled QEMU plumbing). The pipeline/agent orchestration and Claude auth are not implemented yet; `Home` is still a placeholder and the only QEMU command is `qemu_version`. Build new features on the existing seams below.

## Commands

Package manager is pnpm; Rust is edition 2024.

- `pnpm tauri dev`: run the full app. Its before-command runs `pnpm qemu:fetch && pnpm dev`.
- `pnpm dev`: frontend only in a browser (Vite on port 1420). Tauri APIs are absent, so prefs fall back to localStorage.
- `pnpm build`: `tsc` typecheck, then Vite bundle. This is the only frontend check; there is no linter or JS test runner.
- `pnpm tauri build`: production bundle. Its before-command runs `qemu:fetch --required` and `images:fetch --required` (fails if either is missing).
- `pnpm images:fetch [triple] [--required]`: copy the committed plain Alpine image for the target arch from `vendor/images` into `src-tauri/resources/images` (see Agent VM base image).
- `pnpm qemu:fetch [triple] [--required]`: unpack the committed QEMU build for the target from `vendor/qemu` into `src-tauri/resources/qemu` (no network).
- Backend: `cargo build|clippy|test --manifest-path src-tauri/Cargo.toml`. CI runs clippy with `-D warnings`. Single test: `cargo test --manifest-path src-tauri/Cargo.toml <name>`.
- `pnpm driver:install` / `pnpm driver`: install and run `tauri-driver` (into `.tools/`, git-ignored) on port 4444. Use `tauri-driver` (WebDriver) for interactive testing of the running app, not only the browser-based `pnpm dev`, since Tauri APIs, QEMU and the prefs store only exist in the real app.

CI (`ci.yml`) runs `pnpm build`, `cargo build`, clippy and test on Linux (x86_64 and arm64), macOS and Windows. Linux needs `libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf`.

## Architecture

**Frontend (`src/`)**
- `App.tsx` nests FluentProvider (Fluent UI v9), notifications, updates, then a `createHashRouter` (hash routing because the packaged app serves static files). Pages are in `src/pages/`, and `Layout`/`Sidebar` form the shell: no top bar, the sidebar has the app name, Home, Workflow, Sessions, Agent profiles, Runs, About and Settings at the bottom (on mobile a menu button opens it). Settings > General has theme and language (`AppearanceFields`, also step 1 of the welcome dialog; step 2 is the demo content).
- `prefs.ts` holds app preferences. It uses `tauri-plugin-store` (`settings.json`) so Rust can read them too, with a localStorage fallback in a plain browser. `loadPrefs()` must complete before any `getPref` call, and reads are then synchronous from an in-memory cache. New preference keys must be added to the `KEYS` list or they won't be loaded.
- i18n uses i18next with the HTTP backend, so translations are runtime files in `public/locales/{en,ro}/translation.json`. Add every string to both languages.
- `updates.tsx` wraps tauri-plugin-updater. The release endpoint is GitHub `latest.json`.

**Backend (`src-tauri/src/`)**
- `lib.rs` registers plugins (opener, store, updater, process) and commands in `generate_handler!`. New commands must be added there. On Unix, `adopt_shell_path()` runs first in `run()` to import the login shell's PATH, because GUI launches get a minimal PATH. This is how tools like `claude`, nvm and cargo binaries get found. It must stay before any thread spawns because it mutates the environment.
- `qemu.rs`: `command(app, program)` builds a `Command` for any QEMU binary. It uses the bundled tree at `<resource_dir>/qemu/{bin,lib,share/qemu}` (adding `-L share/qemu` for `qemu-system-*`) and falls back to PATH if the build shipped no QEMU. On Windows it sets `CREATE_NO_WINDOW`. Spawn all QEMU processes through it.
- `agent.rs`: the app's end of an agent VM's channel. `drive(stream, bootstrap, task)` takes the VM's virtio-serial socket (any async stream), writes the `Bootstrap`, sends the `Task` when the agent says `ready`, and returns a receiver of everything the agent sends (events, the `final`). Lines are capped at `MAX_MESSAGE`, unparseable lines are skipped, an oversized one ends the run. The stream must stay open until the run is over (see Agent communication). `runs.rs` calls it.
- `secrets.rs`: the Claude setup token lives in the OS credential store (`keyring`), never in `settings.json`. It is write-only from the frontend (`claude_token_set|status|clear`); backend code reads it with `secrets::claude_token()`. Linux needs a running Secret Service.
- `can_self_update()`: on Linux only an AppImage can self-update.
- Tauri permissions live in `src-tauri/capabilities/default.json`. New plugin APIs used from the frontend need entries there.

**QEMU bundling pipeline** (spans several files)
- The built QEMU trees are committed as `vendor/qemu/qemu-<target-triple>.tar.gz` (linux x86_64 and aarch64, macOS x86_64 and aarch64, windows x86_64; checksums in `SHA256SUMS`), so no CI or network is involved.
- `scripts/qemu/fetch.mjs` unpacks the archive for the target triple (`$TAURI_ENV_TARGET_TRIPLE`, else the host) and stamps `.version`. `tauri.conf.json` bundles `resources/qemu/` as `qemu/`. Everything in that directory except its README is git-ignored.
- Upgrading QEMU means building it from source on each OS (Linux builds should use an old glibc, e.g. Ubuntu 22.04; macOS needs the HVF entitlement and ad-hoc signing; the old build script is in git history, commit 932a4de), replacing the archives in `vendor/qemu`, and updating `SHA256SUMS`.

**Agent VM base image** (`scripts/images/`)
- The base image is plain Alpine (`alpine-base`, 8G disk, DHCP on eth0, serial console, no SSH, nothing else), committed as `vendor/images/alpine-<x86_64|aarch64>.qcow2` (~60 MB each, qcow2 compressed). No CI builds it. It was made with `alpine-make-vm-image` v0.13.4 (script in git history, commit 932a4de: `scripts/images/build-plain.sh`), natively per arch; x86_64 boots with BIOS, aarch64 with UEFI.
- Claude Code and `agentd` are **not** in the image yet. The app is meant to install them in a builder VM on the user's machine (Claude Code from the official installer, `agentd` is the script `resources/agentd/agentd.sh`, the same for both arches; also `apk add jq setpriv` (Alpine's own `setpriv` package: busybox's applet lacks `--reuid`, and `setup.sh` checks the real one works), no git), cache the result as the real base, and rebuild when the app updates. Not built yet. The old in-image installer (Claude Code, the `agent` user, the `agentd` OpenRC service) is `scripts/images/provision.sh` in commit 932a4de, the model for that step. The builder VM also needs a way to run commands in the plain image (planned: a first-boot hook that mounts a setup disk and runs its script).
- **Images** (`src-tauri/src/images.rs`, UI Settings > Images, `SettingsImages.tsx`): what agents run on, managed apart from agent profiles. The **base** image (plain Alpine + agentd + Claude Code + ripgrep, `resources/agentd/setup.sh`) is built in and not editable; it is built at startup when missing or stale and on Rebuild. **Custom** images are user-made: name, description, a parent (`base` or another custom image, no cycles), environment variables baked into the image and a shell script that runs as root in a builder VM on top of the finished parent. Files in `<app data>/images/`: `specs/<id>.json` (custom definitions), `built/<id>.qcow2` + `built/<id>.json` (standalone flattened disk + stamp). Stamp: base = hash of `setup.sh`, `agentd.sh`, `agentd.initd` and the plain image's size; custom = hash of the parent's stamp and the script, so a new base, a rebuilt parent (down the chain) or an edited script makes it "stale" (kept usable, rebuilt on request, one build at a time). Saving a custom image starts its build at once (if its parent is built and no other build runs; otherwise it waits for the build button). Baked variables are `export NAME='value'` lines appended to `/etc/conf.d/agentd` (OpenRC sources it, so agentd and the `claude` it runs inherit them; children append to their parent's, later wins; agentd itself knows nothing about them; stored in plain text, no secrets; also part of the stamp). **Starter images and profiles** (first-start welcome dialog, `src/components/Welcome.tsx`, pref `welcomed`): asked once; on yes, `provision_starters` creates the images `developer` (git, github-cli, python3, nodejs, npm, a system-wide git identity) and `qa` (Alpine's chromium + `@playwright/cli`, config in `/etc/playwright-cli.json`, `PLAYWRIGHT_MCP_CONFIG` baked; not verified in a real build) and the profiles `developer` and `qa` on them. Defined in `defaults()` in `images.rs` (scripts in `src-tauri/default-images/*.sh`, compiled in) and `profiles::provision_defaults`. They are ordinary custom images and profiles, existing ids are left alone, and the user can edit or delete them. The images build after the base like any child. On an error the dialog comes back on the next start. It also creates the profiles `orchestrator`, `project-manager`, `delivery-lead`, `business-analyst` (on the base image), `architect`, `reviewer` (on the `developer` image) and the standard workflow (see Workflow). Commands `images_list|save|delete|build` (a deleted image cannot be in use by a profile or be another image's parent). When an image finishes building, the images built directly on it are queued and built next, and theirs after each of them (a chain reaction, one build at a time, state `queued` in the UI; a failed build queues nothing; deleting an image drops it from the queue). A custom image cannot be built (or listed as buildable, `can_build`) until its parent is built. Build output goes through a pipe with `TERM=dumb` (`builder::script_cmd`) so installers print plain lines instead of cursor-addressed redraws. Not built yet: automatic rebuild of stale custom images, and using a profile's image when starting a run.
- **Workflow and sessions** (`src-tauri/src/workflow.rs`, UI `Workflow.tsx` + `WorkflowEditor.tsx`, `Sessions.tsx`, `SessionView.tsx`; there are no projects): the app has one workflow (`<app data>/workflow/workflow.json`) with instructions that every agent gets before its profile's system prompt (`workflow/instructions.json`, `combine_system_prompts`) and any number of sessions (`<app data>/sessions/<sid>.json`: name (empty = untitled, editable), task (the user's first chat message), created, status, `autonomy` `ask|never`). The workflow is an **org chart**, not a sequence: nodes are agents (`profile`, `prompt` = its role in this workflow, `max_calls` = how many times it may be called in a session (1 to 500, bounds loops), `timeout_mins` 1 to 480, default 30) and an edge `A -> B` means A may hand work to B. Other node kinds are the user: `ask` (an agent with an arrow to it may put its questions to the user directly) and `approve` (a gate on the way, `A -> gate -> B`: each handover needs the user's approval). A second edge kind, `before` (dashed, between two agents), is an order: B may be called only after A has finished, within the same coordinator's call; the engine refuses a decision that breaks it and says why, the agent may call them again later (loops); order loops are rejected on save. The **root** is the one node nobody hands work to (it gets the user's request); an agent with outgoing edges is a **coordinator** (it decides what to delegate, in what order, how often: "for each" and review loops are the agents' doing, written in their prompts, there is no loop node), one without is a worker. Edited visually with `@xyflow/react` (select an arrow to set approval). `Workflow::call_edges` (agent to agent, through gates), `ask_node`, `must_precede` and `root` are the views the engine uses. `Workflow::validate` rejects unusable data on save; `problems` (empty, no/many roots, unreachable, unknown profile, unused human node, gate without target) are soft, returned as codes the UI translates. `Workflow::from_json` converts the old step-graph files (start/agent/condition/human/end nodes, a coordinator hub) into an org chart on read (agents and the edges between them stay, edges back to the old coordinator go). `standard_workflow()` (created by the welcome dialog's demo content, and the editor's "Load standard workflow"): orchestrator -> project manager -> delivery lead -> {business analyst, architect, developer, reviewer, tester} with order arrows analyst, architect, developer, reviewer, tester (loops like developer again after a review stay free); no user node, so only the root reaches the user; the rest of the process is in the delivery lead's prompt. Not built: the engine's own choice of how many instances, a separate planner LLM (the coordinators play that role), run views beyond the session page, access of the agents to Jira/GitHub/Confluence (no credentials reach the VM; today only profile env vars, in plain text; ticket text is untrusted input, so use least-privilege tokens).
- **Starting agents** (`src-tauri/src/runs.rs`, UI `Runs.tsx`): `run_vm(app, run_id, image, identity, task, cancel, on_msg)` makes a throwaway qcow2 overlay of the image under `<app data>/runs/tmp/<run>/`, boots it with `images::machine` (shared with the builder: accel with tcg fallback, `-cpu max`, `-nic user`, `-no-reboot`) plus `-action panic=exit-failure`, the virtio-serial `agent` port on a `Serial::named` socket (named pipe on Windows, untested), connects, and hands the channel to `agent::drive` with the `Bootstrap` (identity + token from the keyring) and the `Task`. It always ends with exactly one `Final`: the agent's, or a synthesized `failed` one when the stream ends / QEMU dies (with the tail of QEMU's stderr), the deadline (task timeout + 300 s grace) passes (VM killed) or the run is cancelled. Overlay and VM are removed afterwards. Errors that stop a VM from starting (no token, image not built) are `Err`. The **identity** is a SPIFFE-style label, `spiffe://ccaf.local/<kind>/<id>/.../run/<run>` (`runs::identity`), sent as `Bootstrap.id`, exported to `claude` as `CCAF_AGENT_ID` and written in the log; it is not a credential and nothing verifies it, the channel is the authentication. The `Task` now carries the profile's `system_prompt` (`--append-system-prompt`) and `env` (exported for `claude` only; `agentd` drops invalid names and the reserved ones, values are shell-quoted by jq). Commands `agent_run(profile, prompt)` (returns the run id at once; preflight: profile, token and built image) and `agent_run_cancel`; progress is the `agent-run` event `{run, msg}`, and `<app data>/runs/logs/<run>.jsonl` holds a `start` line and every message (no token). Verified on x86_64 Linux with KVM: `cargo test boots_an_agent_vm -- --ignored --nocapture` boots the built base image (`CCAF_BASE=<path>` for another one) with a fake token: `agentd` runs as a service, `claude` reaches the API (401) and the final arrives, the VM powers off (~20 s). Not verified: a run with a real token, aarch64, macOS, Windows. Not built: no limit on parallel VMs (2 GB each), resuming sessions, the workflow engine that calls this per step.
- **Workflow engine** (`src-tauri/src/engine.rs`, UI `SessionView.tsx`, route `/sessions/:sid`): `drive(host, workflow, task, state, cancel, replies)` runs one session over the org chart; the logic only talks to a `Host` trait (run an agent, log, checkpoint, autonomy), so the tests use a scripted host and `RealHost` boots VMs through `runs::run_vm`. A **call** runs an agent to its end (recursive, `call()`); a worker runs once (`RESULT_SCHEMA`: status, summary, questions, `assumptions`); a coordinator runs in **turns** and answers with a decision (`COORDINATOR_SCHEMA`): `delegate` (up to 5 `{to, instructions}`, run in parallel, each to an agent it has an edge to; the engine refuses anything else and asks again once), `finish` (`result`, `success`: goes to whoever called it; from the root it ends the session) or `ask` (questions it cannot answer: they go back to its caller as `needs_input`, which then answers, asks again or assumes; from the root they go to the user). Every decision carries `notes`, the coordinator's own progress, handed back on its next turn (only within the call: a later call of the same agent starts empty; nothing persists between sessions). **No Claude session is ever resumed**: every run is a fresh VM and each prompt is rebuilt (`worker_prompt`, `coordinator_prompt`): session goal, role, what the caller asked, notes, a compact log of what it handed out, the results since its last turn, its options. The user takes part in two ways only: questions (from the root or from an agent linked to a `You` node; the others pass theirs up to their caller; refused when the session's autonomy is `never` or after 10 questions: the agent is told to assume and to list `assumptions`, shown on the agent's run) and approval gates (always asked, even on `never`; a rejection comes back to the caller as `rejected`). Limits: `max_calls` per agent, depth 8, 60 turns per call, 300 agent runs per session, 4 VMs at once (semaphore). **Resuming** replays: each agent run is journaled in `sessions/<sid>.state.json` under the path of the call (`r`, `r:<round>:<attempt>`, `r/<round>.<i>`...) with an order number; `session_continue` (interrupted, failed or cancelled) first drops the first failed run and everything finished after it (`State::rewind_failures`), then walks the same decisions taking journaled results instead of VMs, so only what never finished runs again (a root that closed the session as failed on its own decision ends the same way). The log is `sessions/<sid>.log.jsonl` (also the `session-log` event): `call_start|call_end` (a call and its parent), `run_start|run_end` (one VM), `agent` (its messages), `decision`, `decision_rejected`, `wait`, `reply`, `error`, `status`; `src/sessionLog.ts` digests it and `SessionView.tsx` shows a live read-only graph of the workflow (node states, active arrows, calls and cost per agent), a side panel with the conversation (task, questions, approvals, result), a timeline and the calls of the clicked agent; at startup running/waiting sessions become `interrupted`. Commands: `session_start(task)|continue|cancel|reply|get|log`, `sessions_create|rename|autonomy|delete`. Preflight (`prepare`): the workflow validates with no problems, every agent's image is built, a token is set. Status: `new | running | waiting | done | failed | cancelled | interrupted`. Tested with the scripted host only (loops over items, parallel calls, refused decisions, questions bubbling up and to the user, `never`, approval gates, limits, resume, cancel); not run against real VMs end to end, no UI test. Not built: a budget limit, a timeout or notification for questions waiting on the user, concurrent session limits, a message to a session that is running or finished (chat after the first message).
- `src-tauri/src/builder.rs` is the builder VM driver: it boots an overlay of the source image with the console on a unix socket (`-serial unix:...`), logs in as root (the plain image has an empty root password and no SSH), switches the tty to no echo / no XON-XOFF, sends files as base64 here-documents (`put`), runs commands with a `DONE-<nonce> <exit>` marker (`run`, streaming cleaned output lines), then `poweroff`, and the app flattens with `qemu-img convert -c`. Builder VMs use `-accel kvm|hvf|whpx -accel tcg -cpu max` (Claude Code's Bun needs SSE4.2, so never the default CPU). They have no virtio agent port, and `agentd.initd` refuses to start without `/dev/virtio-ports/agent`, so the agent does not run (and power the VM off) while a custom image is built. Tests: console driver on the plain image (Linux, needs KVM), and `cargo test builds_the_base_image -- --ignored --nocapture` runs the real base setup (network, ~30 s with KVM). Verified on x86_64 Linux only: the base setup succeeds, `claude --version` works. Not verified: the whole flow through the app (poweroff, convert, rename), a custom image build, a boot of the finished image with agentd as a service, aarch64 (UEFI via `-bios edk2-aarch64-code.fd`), macOS, and Windows (the console is a named pipe there, `-serial pipe:\\.\pipe\ccaf-console-…`, created by QEMU and opened with tokio's `named_pipe` client; it type-checks for `x86_64-pc-windows-gnu` but has never run; the builder also asks for `whpx`, which needs the Windows Hypervisor Platform feature, else it falls back to very slow `tcg`).
- **Agent profiles** (`src-tauri/src/profiles.rs`, UI `src/pages/Profiles.tsx`): created by the user in the UI (the app ships none): name, description, system prompt, environment variables, `model` and `effort` (both optional, `None` = Claude Code's default; effort is `low|medium|high|xhigh|max`), `cpus` (vCPUs, `-smp`; `None` = all the host's cores; QEMU cannot cap CPU time, only core count) and `memory_mb` (`-m`, default 2048, minimum 1024) and the image to run on (`image`, default `base`). Nothing is baked into an image: the system prompt and env travel in the `Task`. Every variable has a value, sent as is in the `Task` (there are no run-time-supplied variables); `PATH`, `HOME`, the Claude token etc. are reserved. Stored as `<id>.json` in `<app data>/profiles/`; commands `profiles_list|save|delete`. Not built yet: sending the system prompt and env in the `Task` (agentd would export the env for `claude` only and pass `--append-system-prompt`).
- The plain image ships inside the app: `scripts/images/fetch.mjs` (`pnpm images:fetch [--required]`, run by the dev and build before-commands) copies `alpine-<arch>.qcow2` for the target (aarch64 targets get aarch64, everything else x86_64) from `vendor/images/` into `src-tauri/resources/images/` (git-ignored), and `tauri.conf.json` bundles it as `images/`.
- Custom images are valid only for the base they were built from (see the stamp above). After an app update with a new base they show "out of date" and keep working until rebuilt. They are built standalone (flattened), not as overlays: the bundled plain image sits in the install directory, which an update replaces and an AppImage mounts at a different path each run, so a backing file would break.
- There is no image or QEMU build in CI: both are committed (`vendor/qemu`, `vendor/images`).
- Image/app version drift: `agentd.sh` is bundled with the app and installed into the base the app builds, so the app and its `agentd` always match; there is no protocol version number.
- The image has no SSH server, and the setup step must fail if one is present
- Boot agents from a throwaway `qemu-img create -b` overlay, never from the base image itself.

**Agent communication**

The app is the hub. Agents never talk to each other; each VM has exactly one channel, a virtio-serial port to the app. There is no message broker, no identity provider and no tokens: the channel belongs to one VM, so the app knows who is talking by which socket a message arrived on. The model is one disposable VM per task:

1. The app boots a QEMU VM from a throwaway overlay of the base image (or the profile's custom image) with `-device virtio-serial-pci -chardev socket,id=agent,path=<sock>,server=on,wait=off -device virtserialport,chardev=agent,name=agent`. The guest sees `/dev/virtio-ports/agent` (created by mdev). **Windows:** the host end of that channel cannot be a unix socket there (tokio has no `UnixStream` on Windows), so use a named pipe: `-chardev pipe,id=agent,path=\\.\pipe\<unique name>` and connect with tokio's `named_pipe` client, the way `builder::Serial` already does for the builder VM's console (reachable only by the current user; do not use TCP on localhost, any local process could reach the agent). Reuse or generalise `Serial` for this. `agent::drive` needs no change, it takes any async stream. The VM launch code does not exist yet, and nothing of the Windows path has run on a real Windows (also needs the Windows Hypervisor Platform for `whpx`, else QEMU falls back to very slow `tcg`).
2. The app connects to the socket and `agent::drive` writes the `Bootstrap` (agent id, Claude setup token). The app keeps this connection open for the whole run: QEMU drops what the guest has not read when the host disconnects, and the VM boots long after the write. Until the app connects, guest reads return end of file, which `agentd` retries.
3. `agentd` starts at boot, reads the bootstrap, answers `ready` (it asks for its task) and the app sends the `Task` (prompt, model, effort, session id, schema, timeout). There are no heartbeats.
4. `agentd` runs `claude` headless (`--output-format stream-json`, partial messages on) and sends every line (thinking, text, tool calls and results, cost) as `kind: "event"` with a sequence number. The app renders the stream live and appends it to the run log.
5. When `claude` stops, `agentd` sends one `final` (status, result, questions, session, cost, exit code), waits until it is written and powers the VM off. There is no mid-run interaction and no MCP server: an agent that needs input ends with questions in its result, and the app decides what to do next (a new run).
6. The app knows a run is over when `final` arrives, or when the stream ends or QEMU exits without one (crash: failed), or its own deadline passes (the task timeout plus a grace period for boot and shutdown: hung, it kills QEMU). QEMU runs with `-no-reboot -action panic=exit-failure` so a guest kernel panic ends QEMU instead of leaving it silent. Either way it kills QEMU if still alive and deletes the overlay.

Messages are one JSON object per line, `{"kind": ..., "body": ...}`, defined in `src-tauri/src/protocol.rs` (the script builds and parses them by hand with `jq`, so keep the two in step; `agentd_e2e.rs` checks they agree). The wire format has no version number: keep changes backward compatible, or release app and image together.

Pieces to build, in this order:
1. (Done.) The channel: `agent.rs` on the app side and `agentd.sh` on the guest side, tested against the real script over two fifos with a fake `claude`.
2. Networking. **For now the guest has full network access**: plain QEMU user-mode networking, `-nic user`, no egress control, no proxy, no guest firewall (`claude` needs the internet to reach its API). Consequences: the VM can reach any internet host, the host's LAN and the host's loopback services at `10.0.2.2:<port>` (the app exposes none today; any it ever exposes must authenticate), and the Claude token in the VM can be sent anywhere by a prompt-injected agent. Do not put more valuable credentials in the VM until egress control exists. The VM test boots with `-nic none`, since the channel needs no network.

   Egress control (deferred, design decided):
   - Seal the NIC in QEMU instead of in the guest: `-nic user,restrict=on,guestfwd=tcp:10.0.2.100:<port>-tcp:127.0.0.1:<host port>` for the proxy only. The guest keeps a NIC and DHCP, but QEMU on the host lets only that forward through, so root in the guest cannot bypass it and no nftables or tunnel is needed. A forward target must already be listening when QEMU starts (the syntax is accepted by the bundled QEMU 11.1.2). Each VM gets its own forward target, so the proxy's listener port identifies the agent. Not verified: that a real guest connects through `guestfwd` under `restrict=on`, how parallel connections behave, whether guest DNS (10.0.2.3) still answers, and that Alpine's DHCP works.
   - Egress proxy in the app (HTTP CONNECT, on `hyper`; `hudsucker` + `rcgen` for inspect mode), deny by default. Rules per profile: `{host regex, ports, mode: tunnel | inspect, inject}`. Host regexes are anchored, lowercase, trailing dot stripped, IDNs as punycode, compiled with the `regex` crate (linear time) and checked in a `RegexSet`; validated when saved. Injection rules name exact hosts, never wildcards, so a token cannot reach another tenant of the same domain. A guard refuses private, loopback and link-local addresses after the name matches (the proxy resolves the name itself and connects to that address). In inspect mode the CONNECT host, the TLS SNI and the `Host` header must agree. One log line per connection with the agent id, and a clear 403 with the reason on denial (it can become an event for the orchestrator, which may ask the user and add a session-scoped rule). `agentd` sets `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`; with the sealed NIC, tools that ignore them fail instead of leaking.

**agentd (built; installed into the image by the app, not yet implemented)**

Code: `src-tauri/resources/agentd/agentd.sh`, a POSIX/busybox `sh` script bundled with the app (`tauri.conf.json` maps `resources/agentd/` to `agentd/`); the messages are `src-tauri/src/protocol.rs`. It needs `jq`, `setpriv` and `setsid` in the image, and nothing else (no git, no compiled code, one file for both arches). Flags: `--channel <path>` (default `/dev/virtio-ports/agent`), `--out <path>` (tests only: a second file for output), `--workspace`, `--claude`, `--run-as <user>` (setpriv to that user with no_new_privs), `--poweroff`. The channel is opened once, read-write (a virtio port cannot be opened twice). Events go through one `jq -cR` that wraps each line with its line number as the sequence, turns non-JSON into `{type: raw}` and replaces lines over 400 KB with a stub; the final is built by `jq` from the `result` line. `claude` runs under `setsid` so a timeout kills its whole process group. `src-tauri/src/agentd_e2e.rs` runs the script with a fake `claude` over fifos (Linux, needs `jq`): a full task and a timeout. Not done yet: the OpenRC service that starts it (`--run-as agent --poweroff`, runlevel default) in the image setup, a boot test in the real image, hidepid/ptrace hardening, a real `claude` run with a valid token. The prompt travels as an argument, so it is limited to ~128 KB. Feeding it to `claude` through stdin instead is a possible later fix, only if the limit is ever hit.

Design:

The program that runs inside each agent VM, one task per boot: it executes the task and reports. A shell script installed in the image by the app as an OpenRC service. Its messages are defined in the app (`protocol.rs`). No SSH, no MCP server, no decisions, no talking to other agents, no state kept between runs.

Lifecycle:
1. Open the virtio-serial port and read the `Bootstrap` (waiting up to 5 minutes for the app to connect): the agent id and the Claude setup token.
2. Answer `ready` and read the `Task`: the prompt, model, thinking level, the result schema and, on a retry, the session to resume.
3. Create the workspace, an empty scratch folder owned by the unprivileged user.
4. Run `claude -p <prompt> --output-format stream-json --verbose --include-partial-messages --model <model> --effort <low|medium|high|xhigh|max> --json-schema <result schema> --session-id <uuid> --dangerously-skip-permissions` (`--resume <id>` instead of `--session-id` on a retry). The token goes only in that process's `CLAUDE_CODE_OAUTH_TOKEN`. The VM is the sandbox, hence no permission prompts. These flags exist in Claude Code 2.1.310; `--effort` takes exactly the levels of the thinking setting, and `--json-schema` gives the structured final answer the orchestrator needs (if a task still ends without it, the planner reads the free text).
5. Send every line `claude` prints as `kind: "event"` with a sequence number. A line that would exceed half the message limit is replaced by a stub with its size and first 4 KB.
6. When `claude` stops, send one `final`: `status` (`done | needs_input | failed`), result, questions, Claude session id, cost and exit code. Wait until it is written, then power the VM off.

Keeping `claude` away from `agentd` (planned; none of it checked against the Alpine image yet):
- Separate users: `agentd` runs as root (or a dedicated `agentd` user) from a root-owned binary and service file; `claude` runs as the unprivileged `agent` user in a workspace only that user owns. `agentd` starts it after `setuid`/`setgid`, with `PR_SET_NO_NEW_PRIVS` and capabilities dropped.
- Nothing to steal from disk: the bootstrap comes over the serial channel and stays in `agentd`'s memory (never a file or command line). The Claude setup token has to be in `claude`'s own environment, nothing else is.
- Hide the process: mount `/proc` with `hidepid=2` and set `kernel.yama.ptrace_scope` to 2 or higher, so `claude` cannot read `agentd`'s `/proc/<pid>` files or ptrace it. Needs checking that the Alpine kernel supports both.
- No escalation path: no `sudo`/`doas`, no root password, and the image setup fails on any setuid/setgid binary outside an allowlist (busybox ships several applets that need stripping), like the SSH check.
- One-way channel: `agentd` spawns `claude` and reads its stdout/stderr through pipes; there is no socket, file or signal for `claude` to command `agentd`. Everything `claude` prints is untrusted data: parsed, wrapped in events, truncated, never run as instructions.
- If `claude` still gets root in the guest, the damage is bounded by the host: the guest has only its own channel, so it can forge its own events, `final` (the app validates and decides the flow itself), and the run timeout ends it. While the guest has full network access, root could also reach the internet, the host's LAN and loopback ports, which is why egress control matters.

Failure handling:
- `claude` fails to start or crashes: send `final` with `failed` and the reason.
- `agentd` itself dies, or never gets its bootstrap or task: it cannot report, so the app sees the stream end, QEMU exit without a `final`, or the run's deadline pass, and marks the run failed (killing the VM in the last case).

**Orchestrator (superseded by the Workflow engine above: delegation through an org chart, no separate planner; kept for the vocabulary)**

The orchestrator is the only party that talks to the user and to agents. Two parts:
- The **engine** (Rust, deterministic, in the app): allocates identities, boots and supervises runs, stores their results, enforces limits (retries, clarification rounds, budget, timeouts) and executes decisions. It is the only thing that can start a run.
- The **planner** (an LLM, itself a Claude Code run in a VM with no tools and no workspace): reads agent results, talks with the user and decides the next step. It answers in a structured decision (`ask_user`, `run_agent`, `done`) that the engine validates before acting. This keeps the engine safe even when the planner is wrong, and needs no API key.

Vocabulary: an **agent** is a logical worker (stable id, role, profile, its task thread); a **run** is one VM execution of an agent with its own short-lived identity. An agent can have several runs.

Clarification loop: `final` carries `status: done | needs_input | failed`, the `questions` when input is needed, the Claude `session` (id and transcript). `agentd` asks Claude to end with a structured answer (`--json-schema`; if it is missing the planner reads the free text). On `needs_input` the engine stores the run, the planner turns the questions into something for the user, the user answers in the UI, and the engine starts a new run for the same agent: the prompt carries the earlier summary plus the Q&A (a transcript cannot be resumed: it dies with the VM). Cap the rounds.

The run store (events, finals, session transcripts) lives on disk in the app data dir, so a conversation survives restarts.

**Workspace transfers will never happen:** the protocol carries no code in either direction (no archive in the `Task`, none in the `final`), and the image has no git. The workspace in the VM is a scratch folder; how an agent gets code and hands work back is decided elsewhere (not by this channel). No folders are shared with the host. Treat everything an agent sends as untrusted: validate the schema and the size.
