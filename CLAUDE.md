# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CC Agent Flows: a Tauri 2 desktop app (React 19 + TypeScript frontend, Rust backend) for running multi-agent, dynamic, end-to-end delivery pipelines built on Claude Code. Design goals:

- Agents run fully sandboxed inside QEMU VMs.
- Authentication uses a Claude Code personal subscription (setup tokens), not API keys.

Current state: projects (see Architecture) and the shell are in place (layout, settings, i18n, theming, auto-update, bundled QEMU plumbing). The pipeline/agent orchestration and Claude auth are not implemented yet; `Home` is still a placeholder and the only QEMU command is `qemu_version`. Build new features on the existing seams below.

## Commands

Package manager is pnpm; Rust is edition 2024.

- `pnpm tauri dev`: run the full app. Its before-command runs `pnpm qemu:fetch && pnpm dev`.
- `pnpm dev`: frontend only in a browser (Vite on port 1420). Tauri APIs are absent, so prefs fall back to localStorage.
- `pnpm build`: `tsc` typecheck, then Vite bundle. This is the only frontend check; there is no linter or JS test runner.
- `pnpm tauri build`: production bundle. Its before-command runs `qemu:fetch --required` and `images:fetch --required` (fails if either is missing).
- `pnpm images:fetch [triple] [--required]`: copy the committed plain Alpine image for the target arch from `vendor/images` into `src-tauri/resources/images` (see Agent VM base image).
- `pnpm qemu:fetch [triple] [--required]`: unpack the committed QEMU build for the target from `vendor/qemu` into `src-tauri/resources/qemu` (no network).
- Backend: `cargo build|clippy|test --manifest-path src-tauri/Cargo.toml`. CI runs clippy with `-D warnings`. Single test: `cargo test --manifest-path src-tauri/Cargo.toml <name>`.
- `pnpm driver:install` / `pnpm driver`: install and run `tauri-driver` (into `.tools/`, git-ignored) on port 4444. **Preferred way to test the UI visually** (screenshots, clicking through pages, reading the DOM): use `tauri-driver` (WebDriver) on the real app, not the browser-based `pnpm dev`, since Tauri APIs, QEMU and the prefs store only exist in the real app. Linux needs `webkit2gtk-driver` (`/usr/bin/WebKitWebDriver`, `sudo apt install webkit2gtk-driver`). The debug binary (`cargo build`, `src-tauri/target/debug/cc-agent-flows`) loads the frontend from Vite, so start `pnpm dev` (port 1420) first, then `pnpm driver`, then `POST /session` with `{"capabilities":{"alwaysMatch":{"tauri:options":{"application":"<path to the binary>"}}}}`; the app uses the real app data dir (images, profiles, sessions). Routes are hash routes (`location.hash = '#/settings'`).

CI (`ci.yml`) runs `pnpm build`, `cargo build`, clippy and test on Linux (x86_64 and arm64), macOS and Windows. Linux needs `libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf`.

## Architecture

**Projects** (the unit the user works in; `config/projects.rs`, `config/scope.rs`, UI `Projects.tsx`, `project/ProjectSettings.tsx`): a project owns its **workflows, sessions, agent profiles, images, variables, secrets and injections** and adds **allowed hosts** and a **system prompt** (`project.json`: name, description, system_prompt, allow_hosts). Files live in `<app data>/projects/<id>/` (`project.json`, `workflows/`, `sessions/`, `profiles/`, `images/{specs,built}`, `variables.json`, `secrets.json`, `injections.json`); a project's secret values are in the keyring as `secret:<project>:NAME`. The **global** settings (Settings, tabs named "Global ...") hold the same kinds in the old locations (`variables.json`, `secrets.json`, `injections.json`, `images/`, `network.json`) and are empty by default, except the Claude API hosts (global allowed hosts, default `api.anthropic.com` and `statsig.anthropic.com`) and the built-in `base` image. `Scope` (`Scope::global()` / `Scope::project(id)`) is how a store says which it works on; the commands take `project: Option<String>` (null = global) for variables, secrets, injections, images, network and demo resets, and `project: String` for profiles, workflows, sessions, session/engine commands, triggers, analytics and `agent_run`. The frontend reads the scope from `useProject()` (null outside a project), so `settings/Images|Secrets|Variables|Injections|Network` are the same components in Settings and in the project's pages. **What a run sees** is the merge of both: variables (`variables::all`, project wins), injections (`injections::available`, project wins by name), secrets (`secrets::secret_value`: the project's, else the global), images (`images::resolve`: the project's, else global, `base` included; a project image may be built on a global one, not the reverse; a project cannot create an image id a global one has), allowed hosts (global + project + profile, `runs::run_vm`; entries may be `${var:NAME}`), the system prompt (global + project + workflow instructions + profile, in that order, `engine/host.rs::prepare`, `runs::agent_run`) and agent profiles (see below). Sessions are keyed `<project>/<sid>` in the engine, `session-log` events carry `project`, trigger/cron/webhook nodes are found across all projects (`triggers::find_all`; the webhook listener and its port are global). Deleting a project removes its directory and secrets and is refused while one of its sessions runs or an image builds. The demo content is the project `demo` (`demo.yaml: project:`, `provision_starters`, returns its id; the `*_reset_demo` buttons show only inside it); creating it moves same-named secrets from the global keyring entries into the project. Image builds are one at a time across all scopes (`Ref` = scope + id, keyed `<project>/<id>` for logs). Older text below that says "Settings > Images/Secrets/Variables/Injections" or `<app data>/profiles` etc. now means the project's page and directory.

**Global system prompt and global profiles** (asked for by the owner): the **global system prompt** (Settings > LLM, `config/system_prompt.rs`, `system_prompt.json` in the app data dir, commands `system_prompt_get|set`, max 64 KB) goes to every agent first; `system_prompt::with_project` is global + project, and `prepare`/`agent_run` add the workflow's and the profile's after it. **Agent profiles** exist globally (Settings tab "Global agent profiles", `<app data>/profiles`) and per project; `profiles_list|save|delete` take `project: Option<String>` (null = global), `profiles_available(project)` is the project's own plus the global ones (the workflow editor, Single runs and the session graph use it; `profiles::available`, a project's profile hides a global one with the same id, and a new project profile never takes a global id). A profile may **extend** another (`Profile::extends`, an id): a project's profile can extend a global one or another of the project, a global one only a global one. `profiles::resolve` (at run start, never at save) builds the profile a run uses: the parents' system prompts first then the child's, env merged by name (child wins), `allow_hosts` and `integrations` added together, and `model`, `effort`, `cpus`, `memory_mb`, `image`, `max_*` taken from the child, else the parent (`memory_mb` and `image` are therefore `Option`; `Profile::memory()` and `image_id()` give the defaults 2048 and `base` on a resolved profile). Integrations, injections and leak detection work on the resolved profile, so `Spec.allow_hosts` includes the parents' hosts. Saving checks the parent exists, is not the profile itself and makes no loop (`check_extends`, max depth 8); deleting is refused while another profile extends it (a global one: in any project). `used_images` counts resolved images, global profiles included. Import/export carries `system_prompt.json` (the file's text replaces ours only on overwrite or when ours is empty) and the global `profiles/` directory (already in `SCOPE_DIRS`). Tested: resolution, loops, parent checks, transfer merge; not run in the real app.

**Integrations** (`config/integrations.rs`, UI `settings/Integrations.tsx`, project page `/p/:pid/integrations`, Settings tab "Global integrations", commands `integrations_list|save|delete`, `<scope dir>/integrations.json`): one place to set up a service (Jira, GitHub). It stores only names (`variables`, `secrets`, `injections` it owns) plus `hosts` and `env` (the agent's environment variables); saving writes the variables, secrets (write-only, value optional when already set) and injections into their own stores (`variables::set`, `secrets::set`, `injections::upsert`), where they stay editable, but `check_free` refuses to delete one that an integration of the same scope names (`variables_delete`, `secrets_delete`, `injections_save`). A profile lists `integrations` (names, project's wins over global); at run start `integrations::expand` adds their env (the profile's own wins on a name) and hosts to the profile's, used by `runs::agent_run` and `RealHost::run_agent` before `injections::prepare`; a missing integration fails the run. Deleting an integration is refused while a profile of the project uses it (global ones are not checked). No built-in presets (decided: the user defines them; "Duplicate" copies one without the secret values). Not run in the real app.

**VM settings** (`config/vm_settings.rs`, `vm.json`, commands `vm_settings_get|set`, UI section in Settings > General `settings/VmSettings.tsx`): accelerator (`auto|hardware|software`; `hardware` has no TCG fallback and fails when the host has none), default vCPUs for profiles without `cpus`, default memory for *new* profiles (the UI pre-fills it, stored profiles keep theirs), VMs at once in the app (read when the app starts, `VmSlots::new`) and per session (`Host::max_vms`), the grace time on top of an agent's timeout, the image script time limit and the builder VM's vCPUs and memory. The network, CPU model, machine type and extra QEMU arguments are deliberately not configurable (they keep the guest sealed and bootable). The export carries only the portable fields (`PORTABLE`: default memory, grace, image script limit), never the hardware-bound ones. Not run in the real app.

**Network limits and leak detection** (`net/egress.rs` `Limits|Meter|Counted`, `net/leaks.rs`, `net/inspect.rs`; asked for by the owner): every run's proxy counts the bytes of the guest's connections in both directions (the guest side, so TLS framing is included) and the open and total connections. Limits: connections at once per agent (global default 64 in `network.json` `max_connections`, Settings > Network; the profile's `max_connections` overrides), data budgets per run (`max_upload_mb`, `max_download_mb`, profile only, unset by default; when one is used up the connections fail and new ones are refused, logged once, and the run is stopped as failed at the next 2 s report, since Claude's own traffic counts and the agent could not reach its API any more). The run reports `{"type":"net","up","down","open","connections"}` events (seq 0) every 2 s when they changed; `RealHost` writes the last ones as a `run_net` log entry, which the analytics fold (per session, agent, day; Analytics page and the session view's per-agent Network panel and node lines use them, speeds are derived from consecutive reports). **Leak detection** (`network.json` `leak_detection`, default on): the secrets a profile's environment takes as `${secret:NAME}` (profile or integration env, values of 8+ characters) may only go to the hosts the *profile and its integrations list* (`Spec.allow_hosts`), not the global or project lists. A request to any other host that carries the value (address, headers, a `Basic` header decoded, percent-encoded, body up to 4 MiB; a larger body to such a host is refused) gets a 403 and a log line (never the value). To read the requests, the run's TLS inspection covers every host that must not receive a protected value (`Inspector::wants`), so those runs terminate TLS for all their hosts (HTTP/1.1 only, no upgrades; tools that pin certificates would fail). It does not catch a transformed value or one sent to a host the profile lists; injected credentials are never in the VM so they are not watched. Tested with fakes (counting, budget, connection limit, refusal in headers/Basic/URL/body); not run against a real VM or real tools.

**Claude accounts mode** (Settings > LLM, `accounts_mode|accounts_set_mode`, `claude-accounts.json`): `round_robin` (default, each run takes the next ready account) or `drain` (always the first ready account in list order until it rests, then the next).

**Frontend (`src/`)**
- `App.tsx` nests FluentProvider (Fluent UI v9), notifications, updates, then a `createHashRouter` (hash routing because the packaged app serves static files). Pages are in `src/pages/`, and `Layout`/`Sidebar` form the shell: no top bar, the sidebar has the app name; outside a project it lists Projects, Global settings and About; Global settings (`/settings/:tab`) replaces the navigation like a project does (back link, General, LLM, Images, Network, Variables, Secrets, Injections), inside one (`/p/:pid/...`, `ProjectRoute` in `src/project.tsx`) a back link, the project's name and its pages (General = name, description, system prompt and delete, then Workflow, Sessions, Agent profiles, Runs, Analytics, Images, Variables, Secrets, Injections, Network = the project's allowed hosts) (on mobile a menu button opens it). `/` is `Projects.tsx`: the projects as cards, a new-project dialog and, while there is no `demo` project, a button that creates it. Settings > General has theme, language, auto-update and the notifications switch (`AppearanceFields`, also step 1 of the welcome dialog; step 2 is the demo content).
- `tauri.ts` has the one `call()` wrapper around `invoke` that pages use. Pages: `pages/session/` (SessionView and its graph/call views), `pages/workflow/` (editor, panels, node), `pages/settings/` (the Settings tabs).
- `prefs.ts` holds app preferences. It uses `tauri-plugin-store` (`settings.json`) so Rust can read them too, with a localStorage fallback in a plain browser. `loadPrefs()` must complete before any `getPref` call, and reads are then synchronous from an in-memory cache. New preference keys must be added to the `KEYS` list or they won't be loaded.
- i18n uses i18next with the HTTP backend, so translations are runtime files in `public/locales/{en,ro}/translation.json`. Add every string to both languages.
- `updates.tsx` wraps tauri-plugin-updater. The release endpoint is GitHub `latest.json`.

**Backend (`src-tauri/src/`)**
- Layout: `config/` (profiles, accounts, secrets, variables, injections, network allowlist), `vm/` (QEMU, `machine.rs` = the QEMU command line and `qemu-img`, images and the builder VM, agent channel, protocol, one agent run), `net/` (egress proxy, TLS inspection, SSH tunnel), `workflow/` (`model.rs` types and validation, `store.rs` files, `commands.rs`, `engine/` = `state`, `prompts`, `decisions`, `run` (the logic and its scripted-host tests), `host` (real host and session commands); plus triggers, cron, webhook, analytics). Top level: `demo.rs` (demo content and the `provision_starters` command), `system.rs`, `util.rs` (time, JSON files, `data_dir`, keyring service name), `lib.rs`. Commands in `generate_handler!` are addressed by their module path, e.g. `workflow::commands::sessions_list`.
- `lib.rs` registers plugins (opener, store, updater, process) and commands in `generate_handler!`. New commands must be added there. On Unix, `adopt_shell_path()` runs first in `run()` to import the login shell's PATH, because GUI launches get a minimal PATH. This is how tools like `claude`, nvm and cargo binaries get found. It must stay before any thread spawns because it mutates the environment.
- `vm/qemu.rs`: `command(app, program)` builds a `Command` for any QEMU binary. It uses the bundled tree at `<resource_dir>/qemu/{bin,lib,share/qemu}` (adding `-L share/qemu` for `qemu-system-*`) and falls back to PATH if the build shipped no QEMU. On Windows it sets `CREATE_NO_WINDOW`. Spawn all QEMU processes through it.
- `vm/agent.rs`: the app's end of an agent VM's channel. `drive(stream, bootstrap, task)` takes the VM's virtio-serial socket (any async stream), writes the `Bootstrap`, sends the `Task` when the agent says `ready`, and returns a receiver of everything the agent sends (events, the `final`). Lines are capped at `MAX_MESSAGE`, unparseable lines are skipped, an oversized one ends the run. The stream must stay open until the run is over (see Agent communication). `vm/runs.rs` calls it.
- `log_entries` (in `workflow/analytics.rs`) reads a session log filtered by kind before parsing (agent events are most of the file). There is no audit export (removed on purpose; do not re-add unasked). **Import/export** (`transfer.rs`, Settings tab "Import / Export" `settings/Transfer.tsx`, commands `transfer_export|import`; asked for by the owner): one encrypted YAML file with everything (global settings, every project's files, image *definitions*, secret values from the keyring, Claude tokens; not session logs, built disks, run logs, app prefs). Argon2id (64 MiB, 3 passes) from the password + XChaCha20-Poly1305 over the whole bundle, YAML only holds the header and a base64 `ciphertext`. The backend picks/writes the file through `tauri-plugin-dialog` (Rust side only) and the plain bundle never reaches the frontend. Import only accepts known relative paths (`classify`), merges by item (variables, secrets index, injections, integrations, allowed hosts, accounts) and never deletes; `overwrite` replaces items that exist, otherwise they stay. Tested: round trip, wrong password, path whitelist, merge; not run end to end in the app.
- `workflow/analytics.rs` (`analytics_get(project: Option<String>)`, null = all projects merged, page `Analytics.tsx`, routes `/p/:pid/analytics` and the main menu's `/analytics`, above About): tokens, duration and run counts per session, per agent profile and per day, folded from the `run_start|run_end` entries of every session log; computed when asked, in a blocking task.
- `workflow/cron.rs`, `workflow/triggers.rs`, `workflow/webhook.rs`: the workflow's trigger nodes (see Workflow and sessions). Last start and error of each cron/webhook node are in `<app data>/triggers.json`.
- Desktop notifications (`Notifier.tsx`, `tauri-plugin-notification`, pref `notifications`, Settings > General): while the window is not focused, the app-wide `session-log` listener notifies on a `wait` (approval or questions) and on a session ending `done|failed`.
- `config/secrets.rs`: named secrets in the OS credential store (`keyring`), never in `settings.json`; write-only from the frontend. Linux needs a running Secret Service.
- `config/accounts.rs` (Settings > LLM, `settings/Llm.tsx`; commands `accounts_list|add|set_token|update|wake|remove`): **Claude accounts**, several setup tokens in the keyring (`claude-account:<id>`; the account `default` is the old single-token entry `claude-setup-token`, so nothing to migrate), names and on/off in `<app data>/claude-accounts.json`. `run_vm` takes an account per attempt, **round-robin** over the enabled ones that are not resting (`accounts::pick`; when all rest, the one that wakes first). A failed run whose text says usage/rate limit (or a rejected/expired token) puts that account to rest (`classify` + `rest`: 1 h for a limit, 12 h for a rejected token, in memory only, a new token or "use it again" lifts it) and, **only if the run used no tokens** (`tokens` empty or 0, so no work is repeated), `run_vm` starts again on the next untried account; mid-run limits after real work are not retried (the account still rests for the next runs). Each attempt emits an `{"type":"account","account":<name>}` event (seq 0; the audit export lists them; the token never leaves the app but into that VM's `Bootstrap`). Detection is by matching the failure text, so a message Claude Code words differently will not be caught: check `classify` against the real messages. Untested with real accounts.
- **Variables** (Settings > Variables, `config/variables.rs`, `settings/Variables.tsx`): named values that are not secret, plain text in `<app data>/variables.json`, commands `variables_list|set|delete` (values are returned to the UI, unlike secrets). `${var:NAME}` works in a profile env value (also inside text, `https://${var:HOST}`) and in an injection's rule host, rule path and user name (`injections::resolved` fills them at run start and validates the whole injection then; saving accepts references unchecked). Resolved last in `injections::build`, so a variable's value is never read as another reference; a missing variable fails the run. Demo: `ATLASSIAN_HOST` and `ATLASSIAN_EMAIL` (`variables::provision_demo`), used by the `JIRA` injection and the profiles' `ATLASSIAN_URL`/`ATLASSIAN_EMAIL`.
- Named secrets (Settings > Secrets, `settings/Secrets.tsx`): values in the keyring (`secret:<NAME>`), names listed in `<app data>/secrets.json` (the store cannot list), commands `secrets_list|set|delete` (write-only, values never returned). A profile env value may contain `${secret:NAME}`; `secrets::resolve_env` fills it in when the run starts (`runs::agent_run`, `RealHost::run_agent`; a missing secret fails the run), so the value reaches the VM's environment for `claude` in plain text until credential injection exists. Image env vars are not resolved (baked in plain text). Not checked at save or in `prepare`, only at run start.
- **App log** (`tauri-plugin-log`, `app.log` in the OS log dir, 2 MB, one rotated copy; About > "View app log" runs `system::app_log_open`, which opens it with the default program): use `log::info!|warn!|error!`. Today it gets the image build lines and failures and failed agent runs.
- `can_self_update()`: on Linux only an AppImage can self-update.
- Tauri permissions live in `src-tauri/capabilities/default.json`. New plugin APIs used from the frontend need entries there.

**QEMU bundling pipeline** (spans several files)
- The built QEMU trees are committed as `vendor/qemu/qemu-<target-triple>.tar.gz` (linux x86_64 and aarch64, macOS x86_64 and aarch64, windows x86_64; checksums in `SHA256SUMS`), so no CI or network is involved.
- `scripts/qemu/fetch.mjs` unpacks the archive for the target triple (`$TAURI_ENV_TARGET_TRIPLE`, else the host) and stamps `.version`. `tauri.conf.json` bundles `resources/qemu/` as `qemu/`. Everything in that directory except its README is git-ignored.
- Upgrading QEMU means building it from source on each OS (Linux builds should use an old glibc, e.g. Ubuntu 22.04; macOS needs the HVF entitlement and ad-hoc signing; the old build script is in git history, commit 932a4de), replacing the archives in `vendor/qemu`, and updating `SHA256SUMS`.

**Agent VM base image** (`scripts/images/`)
- The base image is plain Alpine (`alpine-base` + `linux-virt`, `main` and `community` repos, one ext4 root of 8G with no partition table and no bootloader, DHCP on eth0, empty root password and a serial login for the builder, no SSH, nothing else). It is three files per arch in `vendor/images`: `alpine-<x86_64|aarch64>.qcow2` (~35 MB, qcow2 compressed with zlib: the bundled QEMU is built without zstd), `.vmlinuz` (the arm64 one is the unwrapped `Image`: Alpine ships an EFI zboot wrapper that `-kernel` cannot run) and `.initramfs` (mkinitfs features `base ext4 virtio` only), which QEMU boots directly (`-kernel/-initrd`, `root=/dev/vda`), so there is no BIOS/UEFI/bootloader step and both arches boot the same way. Made by `scripts/images/build-plain.sh <arch> <out>` (needs root, curl, e2fsprogs, qemu-img; natively per arch: x86_64 and aarch64 were built by a throwaway GitHub Actions workflow on `ubuntu-22.04` and `ubuntu-22.04-arm`, which also booted each to the login prompt; the workflow and its runs were deleted; Alpine branch in `scripts/images/version.json`). Redoing the images means running that script on both arches again and replacing the six files. The modules in the root belong to the shipped kernel: an image script that upgrades the kernel breaks the boot (not checked).
- Claude Code and `agentd` are **not** in the image yet. The app is meant to install them in a builder VM on the user's machine (Claude Code from the official installer, `agentd` is the script `resources/agentd/agentd.sh`, the same for both arches; also `apk add jq setpriv openssh-client` (Alpine's own `setpriv` package: busybox's applet lacks `--reuid`, and `setup.sh` checks the real one works), no git), cache the result as the real base, and rebuild when the app updates. Not built yet. The old in-image installer (Claude Code, the `agent` user, the `agentd` OpenRC service) is `scripts/images/provision.sh` in commit 932a4de, the model for that step. The builder VM also needs a way to run commands in the plain image (planned: a first-boot hook that mounts a setup disk and runs its script).
- **Images** (`src-tauri/src/vm/images.rs`, UI Settings > Images, `settings/Images.tsx`): what agents run on, managed apart from agent profiles. The **base** image (plain Alpine + agentd + Claude Code + ripgrep, `resources/agentd/setup.sh`) is built in and not editable; it is built at startup when missing or stale and on Rebuild. **Custom** images are user-made: name, description, a parent (`base` or another custom image, no cycles), environment variables baked into the image and a shell script that runs as root in a builder VM on top of the finished parent. Files in `<app data>/images/`: `specs/<id>.json` (custom definitions), `built/<id>.qcow2` + `built/<id>.json` (standalone flattened disk + stamp). Stamp: base = hash of `setup.sh`, `agentd.sh`, `agentd.initd` and the plain image's size; custom = hash of the parent's stamp and the script, so a new base, a rebuilt parent (down the chain) or an edited script makes it "stale" (kept usable, rebuilt on request, one build at a time). Saving a custom image starts its build at once (if its parent is built and no other build runs; otherwise it waits for the build button). Baked variables are `export NAME='value'` lines appended to `/etc/conf.d/agentd` (OpenRC sources it, so agentd and the `claude` it runs inherit them; children append to their parent's, later wins; agentd itself knows nothing about them; stored in plain text, no secrets; also part of the stamp). **Starter images and profiles** (first-start welcome dialog, `src/components/Welcome.tsx`, pref `welcomed`): asked once; on yes, `provision_starters` creates the images `manager` (on the base: `jtk` (Jira CLI) from `open-cli-collective/atlassian-cli`, binary in `/usr/local/bin`; the repo holds several tools, so the script picks the newest `jtk-v*` tag from the release list; it reads `ATLASSIAN_URL`, `ATLASSIAN_EMAIL` and `JIRA_API_TOKEN` from the environment, which the demo profiles set, the token as `${injection:JIRA}`, no config file; not verified in a real build), `developer` (on `manager`: git, github-cli, python3, nodejs, npm, a system-wide git identity) and `qa` (on `manager`: Alpine's chromium + the `agent-browser` musl binary from its latest GitHub release, no Node; `AGENT_BROWSER_EXECUTABLE_PATH` and `AGENT_BROWSER_ARGS` (`--no-sandbox`) baked; not verified in a real build) and the profiles `developer` and `qa` on them. The demo content also creates three secrets (`GITHUB_TOKEN`, `GITHUB_READONLY_TOKEN`, `JIRA_TOKEN`; value `dummy`, `secrets::provision_demo`) and one injection each (`GITHUB[_READONLY]` is Basic `x-access-token` on github.com and api.github.com, `JIRA` is Basic on `${var:ATLASSIAN_HOST}` with `${var:ATLASSIAN_EMAIL}` (variables, Settings > Variables; placeholders to edit), path `/rest/*`). Read-only (GitHub) is the token's scope, not a proxy rule (git, `gh` and Jira search read with POST). Profiles get them through their `env` in the demo file: `GH_TOKEN` is `GITHUB` for the developer and the reviewer (who also approves and merges) and `GITHUB_READONLY` for architect and qa; `JIRA_API_TOKEN` (one token, no read-only variant; plus `ATLASSIAN_URL` = `https://${var:ATLASSIAN_HOST}` and `ATLASSIAN_EMAIL` = `${var:ATLASSIAN_EMAIL}`) go to project manager, business analyst, architect, developer, reviewer and qa. The starter images carry their tools' docs (see Tool docs below): `manager` the `jtk` help pages, `qa` `agent-browser --help`, written from the tools' own output at build time (not tested in a VM). Developer and reviewer share one GitHub token (one account), so GitHub refuses the reviewer's approve/request-changes on the developer's pull request; the reviewer's prompt says to leave an APPROVED / CHANGES REQUESTED comment instead. Jira has one token for all, so "only the project manager moves tickets" is a rule in the prompts, not enforced. **Agent communication**

The app is the hub. Agents never talk to each other; each VM has exactly one channel, a virtio-serial port to the app. There is no message broker, no identity provider and no tokens: the channel belongs to one VM, so the app knows who is talking by which socket a message arrived on. The model is one disposable VM per task:

1. The app boots a QEMU VM from a throwaway overlay of the base image (or the profile's custom image) with `-device virtio-serial-pci -chardev socket,id=agent,path=<sock>,server=on,wait=off -device virtserialport,chardev=agent,name=agent`. The guest sees `/dev/virtio-ports/agent` (created by mdev). **Windows:** the host end of that channel cannot be a unix socket there (tokio has no `UnixStream` on Windows), so use a named pipe: `-chardev pipe,id=agent,path=<unique name>` (QEMU adds `\\.\pipe\` itself; the client opens the full path) and connect with tokio's `named_pipe` client, the way `builder::Serial` already does for the builder VM's console (reachable only by the current user; do not use TCP on localhost, any local process could reach the agent). Reuse or generalise `Serial` for this. `agent::drive` needs no change, it takes any async stream. The VM launch code does not exist yet, and nothing of the Windows path has run on a real Windows (also needs the Windows Hypervisor Platform for `whpx`, else QEMU falls back to very slow `tcg`).
2. The app connects to the socket and `agent::drive` writes the `Bootstrap` (agent id, Claude setup token). The app keeps this connection open for the whole run: QEMU drops what the guest has not read when the host disconnects, and the VM boots long after the write. Until the app connects, guest reads return end of file, which `agentd` retries.
3. `agentd` starts at boot, reads the bootstrap, answers `ready` (it asks for its task) and the app sends the `Task` (prompt, model, effort, session id, schema, timeout). There are no heartbeats.
4. `agentd` runs `claude` headless (`--output-format stream-json`, partial messages on) and sends every line (thinking, text, tool calls and results, token usage) as `kind: "event"` with a sequence number. The app renders the stream live and appends it to the run log.
5. When `claude` stops, `agentd` sends one `final` (status, result, questions, session, tokens, exit code), waits until it is written and powers the VM off. There is no mid-run interaction and no MCP server: an agent that needs input ends with questions in its result, and the app decides what to do next (a new run).
6. The app knows a run is over when `final` arrives, or when the stream ends or QEMU exits without one (crash: failed), or its own deadline passes (the task timeout plus a grace period for boot and shutdown: hung, it kills QEMU). QEMU runs with `-no-reboot -action panic=exit-failure` so a guest kernel panic ends QEMU instead of leaving it silent. Either way it kills QEMU if still alive and deletes the overlay.

Messages are one JSON object per line, `{"kind": ..., "body": ...}`, defined in `src-tauri/src/vm/protocol.rs` (the script builds and parses them by hand with `jq`, so keep the two in step; `vm/agentd_e2e.rs` checks they agree). The wire format has no version number: keep changes backward compatible, or release app and image together.

Pieces to build, in this order:
1. (Done.) The channel: `vm/agent.rs` on the app side and `agentd.sh` on the guest side, tested against the real script over two fifos with a fake `claude`.
2. (Done for agent VMs.) Networking. Agent VMs have a **sealed NIC**: user-mode networking with `restrict=on`, so the only way out is one SSH tunnel to the app's egress proxy, deny by default (see below). Builder VMs (which run package managers and the user's image scripts) still have plain `-nic user`, open internet, as does the VM of anyone running QEMU by hand. Consequences for agents: the VM reaches only the hosts of the allowlists (HTTPS, port 443), not the LAN, not the host's loopback (`10.0.2.2`), not other ports; the Claude token in the VM can still go to an allowlisted host, so keep the lists short. Keep tokens with more value out of the VM until credential injection exists. The channel test (`vm/agentd_e2e.rs`) needs no network at all.

   Egress control (built; credential injection and TLS inspection are not):
   - Allowlists: global in Settings > Network (`config/network.rs`, `<app data>/network.json`, defaults `api.anthropic.com` and `statsig.anthropic.com`) and per profile (`Profile::allow_hosts`; the starter profiles developer, architect, reviewer and qa get github (`github.com`, `api.github.com`, the injection's hosts) and the npm/pip registries; those and the project manager and business analyst get `${var:ATLASSIAN_HOST}` (the `JIRA` injection's host) and `api.media.atlassian.com` (Jira attachments)). Entries are `host` or `*.host` (subdomains only, not the bare host), HTTPS port 443 only, normalized by `profiles::clean_host`. A run's rules are the union of the two (`egress::Rules`). An empty global list cuts agents off from the Claude API.
   - **Transport: seal the NIC in QEMU, tunnel through SSH** (`runs::sealed_nic`, `net/tunnel.rs`). `-nic user,restrict=on,guestfwd=tcp:10.0.2.100:22-tcp:127.0.0.1:<port>`: the guest keeps a NIC and DHCP, but QEMU on the host lets only that forward through, so root in the guest cannot bypass it and no nftables is needed. `agentd` runs `ssh -f -N -L 127.0.0.1:3128:egress:3128 agent@10.0.2.100` (OpenSSH client, `openssh-client` in `setup.sh`; dropbear's `dbclient` lacks what we need) to an SSH server inside the app (`russh` with the `ring` backend, `tunnel::Tunnel`, one per run, listening on a loopback port before QEMU starts) and exports `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` (and lowercase) for `claude` only, after the profile's variables so they cannot override them (Claude Code does not support SOCKS, hence `-L` to the HTTP proxy, not `-D`). The server accepts one thing: the run's own key (a per-run ed25519 pair generated by the app and sent in `Bootstrap.tunnel`; `agentd` writes the private key to a root-only temp file, ssh reads it and `agentd` deletes it at once, `claude` runs as another user and never sees it) and `direct-tcpip` channels to `egress:3128`; sessions, shells, exec, subsystems, X11 and remote forwarding are refused. The image has no SSH *server*; the client is fine (`setup.sh` fails if `sshd`, dropbear, sudo or doas are present). The tunnel is not restarted if it dies: the chardev does not reconnect, so a dead tunnel means no network and the run fails or times out. Without `Bootstrap.tunnel` (old app, tests) `agentd` sets up no proxy.
   - Why SSH: `guestfwd` has two forms. `-tcp:` / `-chardev:` connect QEMU to **one** host connection and share it as a single byte stream for all the guest's connections, so only the guest's first connection works and the rest get `punt!` (tested; known and documented: the `cmd:` form was added in 2011 for this reason; `mux=on` only shares a chardev between consoles, it does not separate connections). `-cmd:<relay>` starts a process per guest connection (inetd style, the relay pipes stdin/stdout to `127.0.0.1:<port>`) and works, but whether libslirp supports it on macOS and Windows is unknown. SSH fits the single-stream form: the whole session is one TCP connection that multiplexes the channels, so it needs nothing but `guestfwd=tcp:`, which is portable. Fallback if the SSH server proves too heavy: `-cmd:` with the app's own binary as the relay (`--relay <port>`).
   - Verified on x86_64 Linux with KVM, QEMU 11.1.2, base image with `openssh-client`: `cargo test boots_an_agent_vm -- --ignored` (3 runs of 3 passed): `agentd` as a service opens the tunnel through `guestfwd=tcp:`, `claude` (fake token) reaches `api.anthropic.com` through it (401, 11 CONNECTs allowed, none denied) and the VM powers off. Earlier, with a `-cmd:nc` relay and a throwaway proxy: `restrict=on` leaves DHCP working, direct connections to the internet and to `10.0.2.2` fail, guest DNS (10.0.2.3) does not answer (fine: the client sends names to the proxy), 8 parallel connections reach the proxy. Unit tests: `net/egress.rs` (rules, address guard, denials, tunnelling), `net/tunnel.rs` (real SSH client: wrong key refused, only the proxy channel opens, 4 parallel CONNECTs, a denied host gets 403), `vm/agentd_e2e.rs` (the script with a fake `ssh`: arguments, key removed, proxy variables, failure when the tunnel does not open). Not verified: a denied host from inside a real guest, git/npm/pip/`gh` through the proxy, macOS, Windows, aarch64, a run with a real token. The SSH banner goes out when QEMU connects, before the guest connects; it worked (QEMU leaves it in the socket buffer until the guest reads), if it ever stalls, make the server wait for the client's first bytes.
   - Egress proxy (`net/egress.rs`): HTTP `CONNECT` on any async stream (the SSH channels), tunnel mode only, deny by default: the host must be on the run's rules, the port must be 443, IP literals are refused, and the proxy resolves the name itself and connects to an address that passes the guard (private, loopback, link-local, CGNAT, multicast, reserved and the IPv6 equivalents are refused, so an allowed name cannot reach the host or LAN). 403 with the reason on denial, one log line per connection (shown as `egress` events), at most 64 connections per run. `agentd` sets the proxy variables; with the sealed NIC, tools that ignore them fail instead of leaking. Planned on top (inspect mode, on `hudsucker` + `rcgen`): per-profile rules `{host, mode: tunnel | inspect, inject}`, with injection naming exact hosts, never wildcards; the CONNECT host, the TLS SNI and the `Host` header must agree. The denial could become an event for the orchestrator, which may ask the user and add a session-scoped rule.
   - **The Claude token is injected too** (`injections::claude`, built in: not stored, not listed in Settings > Injections, not editable). `run_vm` adds it to each attempt's injections, last so no user injection overrides it: every request to `api.anthropic.com` (any path, any method) gets `Authorization: Bearer <token>`. The `Bootstrap` and `CLAUDE_CODE_OAUTH_TOKEN` carry only `CLAUDE_PLACEHOLDER`, so the real token never enters the VM and every run goes through TLS inspection (a CA per run is always in the bootstrap). `statsig.anthropic.com` stays tunnelled. `api.anthropic.com` must still be in the allowlist. **Not run with a real token:** it assumes `claude` accepts the placeholder, sends it as `Authorization: Bearer`, and trusts the run CA through `NODE_EXTRA_CA_CERTS`/the system bundle; the base image must be rebuilt for the current `agentd.sh` (CA install). If `claude` checks the token's format or uses another header, adjust `claude()` / the placeholder. This replaces the "token in the VM" caveats elsewhere in this file.
- Credential injection (built, `config/injections.rs` + `net/inspect.rs`; tokens stay out of the VM): Settings > Injections (`settings/Injections.tsx`, `<app data>/injections.json`). An injection has a name, rules (`host` or `*.host`, path glob where `*` matches anything including `/`, methods; empty = all), a header (default `Authorization`; framing headers refused), a format (`bearer`, `basic` with a user name, `raw`), a value source (`source`: a secret from Settings > Secrets, the default; a variable, name in `value`; or a fixed text in `value`, plain text, not for credentials) and an optional placeholder (default `ccaf-injected`). A profile env value `${injection:NAME}` expands to the placeholder (all the VM sees, for tools that refuse to run without a token) and switches the injection on for that run (`injections::prepare`, called by `runs::agent_run` and `RealHost::run_agent`; a missing injection or secret fails the run). The injection's hosts are **not** added to the run's allowlist: they must be listed in the profile's `allow_hosts` (or Settings > Network), else the run does not start (`runs::run_vm`, `Rules::covers`). An `allow_hosts` entry may be `${var:NAME}` (resolved at run start by `resolve_hosts`, checked as a host then; saving accepts it unchecked). The proxy hands those hosts (not the others, which stay tunnelled, `api.anthropic.com` included) to `Inspector` after the `200`: TLS is terminated with a leaf certificate made for the host and signed by a **CA generated per run** (its key never leaves the app; the certificate goes in `Bootstrap.ca`, `agentd` appends it to `/etc/ssl/certs/ca-certificates.crt` and a file for `NODE_EXTRA_CA_CERTS`/`REQUESTS_CA_BUNDLE`), the requests are read with hyper (HTTP/1.1 only, upgrades refused), the TLS SNI and the `Host` header must be the `CONNECT` host (else 421), matching requests get the header set (replacing the client's), and they go on over a new TLS connection checked against the Mozilla roots (`webpki-roots`). A path with dot segments, encoded `.`/`/` or a backslash never matches, so a rule cannot be stretched by traversal. The log says `egress: GET host/path gets NAME`, never the value. Tested with a real TLS client and server in `net/inspect.rs` (replacement, method/path/host mismatches, traversal, SNI) and the `agentd` side with fakes; **not** run against a real VM, `gh`, `git` or a real Atlassian site, and the base image must be rebuilt for the new `agentd.sh`. Not done: a CIDR/IP-literal host, WebSockets, response inspection, rate or body limits, a denial turned into a question for the user.

4. (Done.) Protocol: JSON messages in a shared Rust crate. The TypeScript types of the wire messages are generated from it (`ts-rs`, a dev-dependency: `cargo test export_bindings` writes `src/generated/*.ts`; commit the result when `vm/protocol.rs` changes).
5. UI: a run page with the live event stream, backed by the run log on disk (also gives replay).
6. (Done, see Workflow engine.) Orchestration: the engine runs the org chart on top of the messages. There is no direct agent-to-agent chat.

**Fast boot** (agent VMs; builders keep the stock boot): QEMU boots the shipped kernel and initramfs directly (see Agent VM base image) with `init=/sbin/ccaf-init` (`resources/agentd/ccaf-init.sh`, installed by `setup.sh`, part of the base stamp together with the kernel and initramfs sizes). It is PID 1 and does only: mount proc (`hidepid=2`), sys, dev, devpts, tmpfs for /run, /tmp and /dev/shm, `ptrace_scope=2` (if the kernel has Yama), mdev for `/dev/virtio-ports/agent`, a **static** network (10.0.2.15/24 via 10.0.2.2, no DHCP), sources `/etc/conf.d/agentd` (baked image variables), runs `agentd --run-as agent --poweroff` in the foreground, and powers off if it returns. OpenRC stays installed (packages and image scripts may use it) but agent runs never start it. `agentd` ends with `poweroff -f` (the disk is a throwaway overlay). The NIC is `virtio-net-pci` (the initramfs has that driver, not e1000), the disk has `cache=unsafe`, the machine has `-nodefaults` (no VGA, CD-ROM, floppy), the kernel runs `quiet`, built images are not compressed (`vm/images.rs` converts without `-c`) and a profile without `cpus` gets at most 4 vCPUs. `setup.sh` also strips every setuid/setgid bit and fails if one is left (busybox `su` would accept the plain image's empty root password), so the agent cannot become root. `cargo test boots_an_agent_vm` prints `TIMING` lines. Not done: microvm, snapshots or a pool of pre-booted VMs (declined), checking that an image script did not upgrade the kernel.

**agentd (built; installed into the image by the app's base build, `setup.sh`)**

Code: `src-tauri/resources/agentd/agentd.sh`, a POSIX/busybox `sh` script bundled with the app (`tauri.conf.json` maps `resources/agentd/` to `agentd/`); the messages are `src-tauri/src/vm/protocol.rs`. It needs `jq`, `setpriv`, `setsid` and, for the egress tunnel, the OpenSSH client and busybox `timeout` in the image, and nothing else (no git, no compiled code, one file for both arches). Flags: `--channel <path>` (default `/dev/virtio-ports/agent`), `--out <path>` (tests only: a second file for output), `--workspace`, `--claude`, `--ssh` (tests), `--run-as <user>` (setpriv to that user with no_new_privs), `--poweroff`. The channel is opened once, read-write (a virtio port cannot be opened twice). Events go through one `jq -cR` that wraps each line with its line number as the sequence, turns non-JSON into `{type: raw}` and replaces lines over 400 KB with a stub; the final is built by `jq` from the `result` line. `claude` runs under `setsid` so a timeout kills its whole process group. `src-tauri/src/agentd_e2e.rs` runs the script with a fake `claude` over fifos (Linux, needs `jq`): a full task, a timeout, and the tunnel (with a fake `ssh`). Not done yet: the OpenRC service that starts it (`--run-as agent --poweroff`, runlevel default) in the image setup, a boot test in the real image, hidepid/ptrace hardening, a real `claude` run with a valid token. The prompt travels as an argument, so it is limited to ~128 KB. Feeding it to `claude` through stdin instead is a possible later fix, only if the limit is ever hit.

Design:

The program that runs inside each agent VM, one task per boot: it executes the task and reports. A shell script installed in the image by the app as an OpenRC service. Its messages are defined in the app (`vm/protocol.rs`). No SSH, no MCP server, no decisions, no talking to other agents, no state kept between runs.

Lifecycle:
1. Open the virtio-serial port and read the `Bootstrap` (waiting up to 5 minutes for the app to connect): the agent id and the Claude setup token.
2. Answer `ready` and read the `Task`: the prompt, model, thinking level, the result schema and, on a retry, the session to resume.
3. Create the workspace, an empty scratch folder owned by the unprivileged user.
4. Run `claude -p <prompt> --output-format stream-json --verbose --include-partial-messages --model <model> --effort <low|medium|high|xhigh|max> --json-schema <result schema> --session-id <uuid> --dangerously-skip-permissions` (`--resume <id>` instead of `--session-id` on a retry). The token goes only in that process's `CLAUDE_CODE_OAUTH_TOKEN`. The VM is the sandbox, hence no permission prompts. These flags exist in Claude Code 2.1.310; `--effort` takes exactly the levels of the thinking setting, and `--json-schema` gives the structured final answer the orchestrator needs (if a task still ends without it, the planner reads the free text).
5. Send every line `claude` prints as `kind: "event"` with a sequence number. A line that would exceed half the message limit is replaced by a stub with its size and first 4 KB.
6. When `claude` stops, send one `final`: `status` (`done | needs_input | failed`), result, questions, Claude session id, tokens and exit code. Wait until it is written, then power the VM off.

Keeping `claude` away from `agentd` (planned; none of it checked against the Alpine image yet):
- Separate users: `agentd` runs as root (or a dedicated `agentd` user) from a root-owned binary and service file; `claude` runs as the unprivileged `agent` user in a workspace only that user owns. `agentd` starts it after `setuid`/`setgid`, with `PR_SET_NO_NEW_PRIVS` and capabilities dropped.
- Nothing to steal from disk: the bootstrap comes over the serial channel and stays in `agentd`'s memory (never a file or command line). The Claude setup token has to be in `claude`'s own environment, nothing else is.
- Hide the process: mount `/proc` with `hidepid=2` and set `kernel.yama.ptrace_scope` to 2 or higher, so `claude` cannot read `agentd`'s `/proc/<pid>` files or ptrace it. Needs checking that the Alpine kernel supports both.
- No escalation path: no `sudo`/`doas`, no root password, and the image setup fails on any setuid/setgid binary outside an allowlist (busybox ships several applets that need stripping), like the SSH check.
- One-way channel: `agentd` spawns `claude` and reads its stdout/stderr through pipes; there is no socket, file or signal for `claude` to command `agentd`. Everything `claude` prints is untrusted data: parsed, wrapped in events, truncated, never run as instructions.
- If `claude` still gets root in the guest, the damage is bounded by the host: the guest has only its own channel, so it can forge its own events, `final` (the app validates and decides the flow itself), and the run timeout ends it. The NIC is sealed (see Egress control): root in the guest can use the tunnel and so reach the allowlisted hosts, nothing else, so a prompt-injected agent can still send the Claude token to an allowlisted host: keep the lists short.

Failure handling:
- `claude` fails to start or crashes: send `final` with `failed` and the reason.
- `agentd` itself dies, or never gets its bootstrap or task: it cannot report, so the app sees the stream end, QEMU exit without a `final`, or the run's deadline pass, and marks the run failed (killing the VM in the last case).

**Orchestrator (superseded by the Workflow engine above: delegation through an org chart, no separate planner; kept for the vocabulary)**

The orchestrator is the only party that talks to the user and to agents. Two parts:
- The **engine** (Rust, deterministic, in the app): allocates identities, boots and supervises runs, stores their results, enforces limits (retries, clarification rounds, budget, timeouts) and executes decisions. It is the only thing that can start a run.
- The **planner** (an LLM, itself a Claude Code run in a VM with no tools and no workspace): reads agent results, talks with the user and decides the next step. It answers in a structured decision (`ask_user`, `run_agent`, `done`) that the engine validates before acting. This keeps the engine safe even when the planner is wrong, and needs no API key.

Vocabulary: an **agent** is a logical worker (stable id, role, profile, its task thread); a **run** is one VM execution of an agent with its own short-lived identity. An agent can have several runs.

Clarification loop: `final` carries `status: done | needs_input | failed`, the `questions` when input is needed, the Claude `session` (id and transcript). `agentd` asks Claude to end with a structured answer (`--json-schema`; if it is missing the planner reads the free text). On `needs_input` the engine stores the run, the planner turns the questions into something for the user, the user answers in the UI, and the engine starts a new run for the same agent: the prompt carries the earlier summary plus the Q&A (a transcript cannot be resumed: it dies with the VM). Cap the rounds.

The run store (events, finals, session transcripts) lives on disk in the app data dir, so a conversation survives restarts.

**Workspace transfers will never happen:** the protocol carries no code in either direction (no archive in the `Task`, none in the `final`), and the image has no git. The workspace in the VM is a scratch folder; how an agent gets code and hands work back is decided elsewhere (not by this channel). No folders are shared with the host. Treat everything an agent sends as untrusted: validate the schema and the size.
